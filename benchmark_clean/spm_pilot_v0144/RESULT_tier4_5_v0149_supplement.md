# spm pilot Tier 4.5 — v0.1.49 Netgen supplement program (empirical run)

Follow-up to `RESULT_tier4_5_lvs_attempts.md` and `PHASE_C_CLEANUP_RESULT.md`. The external review proposed a 3-step open-source closure path (Netgen setup-file + KLayout cross-check + Magic extraction tuning). The Vibe-IC doctrine ("write a program if the rule is deterministic") says the Netgen setup-file step belongs in the plugin as a deterministic emitter, not as a per-design hand-authored TCL.

## Headline

**Shipped**: `programs/lvs_netgen_setup_emit.py` — a deterministic Netgen LVS supplementary setup TCL emitter for sky130A / gf180mcuC / gf180mcuD. 33 pytest cases covering rules 1-5. Wired into `mcp-eda-server` `eda_lvs` as an optional `setup_supplement` parameter (v2.7.0).

**Empirically**: applied to the spm Tier 4.5 case (`chip_top.spice` 261 devices / 453 nets vs `chip_top_pnr_with_pwr.v` 261 devices / 1330 nets). The 14-global + 2-flatten supplement loaded cleanly into Netgen — zero TCL errors, all rules applied, `LVS_SETUP_APPLIED` audit lines surfaced — but the **net-count mismatch was unchanged** (453 vs 1330). The dominant gap in this specific case is **interconnect-naming** (Magic's hierarchical `_465_/CLK` vs Yosys's flat `wire _001_;`), not power-net globalisation. The program ships correct + tested, designs whose gap IS power-globalisation would close fully.

## What the program does (deterministic rules 1-5)

| Rule | Action | Source |
|---|---|---|
| 1 | `global vccd1` × N power-net declarations | PDK-keyed default list (14 for sky130A; 4 for gf180); `--extra-power-net` extends |
| 2 | Stdcell library-name equivalence | NO emit (foundry setup's wildcard loop owns it); audit-comment surfaces the dependency |
| 3 | Symmetric-MOS source-drain | NO emit (foundry default-symmetric already covers); comment-only |
| 4 | `flatten class` directives | Opt-in via `--flatten-top-a` + `--flatten-top-b`; both-sides-or-neither, empty by default |
| 5 | tap/fill/decap `ignore class` | NO emit (foundry setup gated by `MAGIC_EXT_USE_GDS=1`); comment surfaces the env-var dependency |

The deliberate non-emission of rules 2/3/5 (instead surfacing them as audit comments) prevents the Netgen `equate classes`/`permute default` re-declaration warnings that hand-authored TCL routinely tripping over.

## Usage

```bash
# Generate the supplement
python3 programs/lvs_netgen_setup_emit.py \
    --pdk sky130A \
    --flatten-top-a chip_top \
    --flatten-top-b chip_top \
    --audit-comments \
    --out lvs_setup_supplement.tcl

# Concatenate with foundry setup and run Netgen
cat $PDK_ROOT/sky130A/libs.tech/netgen/sky130A_setup.tcl \
    lvs_setup_supplement.tcl \
    > lvs_combined_setup.tcl

netgen -batch lvs "chip_top.spice chip_top" \
                   "chip_top_pnr_with_pwr.v chip_top" \
                   lvs_combined_setup.tcl \
                   lvs_v0149_report.txt
```

Or via `mcp-eda-server` `eda_lvs` (v2.7.0+):

```javascript
eda_lvs({
  mode: "netgen",
  layout_netlist: "/path/to/chip_top.spice",
  schematic_netlist: "/path/to/chip_top_pnr_with_pwr.v",
  top_module: "chip_top",
  pdk: "sky130",
  setup_supplement: "/path/to/lvs_setup_supplement.tcl",
})
```

## Empirical run on spm Tier 4.5 (v0146 baseline)

Inputs (unchanged from `RESULT_tier4_5_lvs_attempts.md`):
- Layout: `lvs_v0146/chip_top.spice` (Magic ext2spice; 453 nets / 259 devices)
- Schematic: `lvs_v0146/chip_top_pnr_with_pwr.v` (OpenROAD write_verilog -include_pwr_gnd; 1330 nets / 259 devices)
- Foundry: `sky130A_setup.tcl`
- Supplement: `lvs_setup_supplement.tcl` (generated by program; 14 globals + 2 flatten)

Result:

...
Circuit 1 contains 259 devices, Circuit 2 contains 259 devices.

**The supplement loaded cleanly** (no parse errors, audit lines surfaced, devices stayed at 259=259 = matches v0146 baseline). **Net mismatch unchanged** because the dominant cause is interconnect-naming, not power-globalisation — confirmed by the unchanged 453 vs 1330 count (which appeared in Tier 4.5 Attempt 1 with bare Magic ext2spice options too).

## Path-2 LEF-with-obs side experiment

While the user's "go 1" was the LEF-with-obs option from `PHASE_C_CLEANUP_RESULT.md` § 3 routes, I quickly regenerated `spm.lef` with OpenROAD `write_abstract_lef -bloat_occupied_layers` (the closest flag — OpenROAD 2023.07 has no `-include_obs` per se). The regenerated LEF has 8 OBS LAYER entries (nwell/pwell/li1/met1-5), matching what `-include_obs` would surface. **But it does not change the wrapper GDS**: Phase B streamed the macro `spm.gds` (not the LEF abstract) into the wrapper area, so the precheck XOR delta is independent of the macro's LEF obstruction layers. Empirical conclusion: in this OpenLane flow, regenerating `spm.lef` with obs layers helps downstream wrapper PnR (avoids over-the-macro routing) but does NOT move precheck's XOR delta or LAYOUT check.

This confirms (again) that the practical chipignite remediation for the remaining 2 FAILs is **waiver entry** — not LEF tweaks, not flatten flow.
