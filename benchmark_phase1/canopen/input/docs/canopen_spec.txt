CiA 301

CANopen Application Layer and Communication Profile

CiA Draft Standard Proposal 301
Version 4.2.0

CAN in Automation (CiA) e. V.
Kontumazgarten 3, DE-90429 Nuremberg

CANopen is the standardized higher-layer (application layer) communication
protocol that runs on top of a Controller Area Network (CAN) data link layer
and physical layer. CiA 301 specifies the CANopen application layer, the
communication profile, the object dictionary, and the communication objects
that a CANopen device must implement. CANopen is registered as the European
standard EN 50325-4.


1  Scope

This specification defines the CANopen application layer and communication
profile. CANopen uses the services and frame format of the underlying CAN bus
(ISO 11898) but adds the application-layer structure that makes CAN-based
devices interoperable: an object dictionary, a predefined set of communication
objects (PDO, SDO, NMT, SYNC, TIME, EMCY, heartbeat), a defined boot-up and
network-management state machine, and a default identifier (COB-ID) allocation
scheme. CANopen does NOT redefine the CAN frame, CAN arbitration, CAN bit
stuffing, or the CAN error frame; those remain as defined by the CAN data link
layer. CANopen is the application layer ABOVE CAN.

4  Reference model

The CANopen communication model is built on the producer/consumer and the
client/server interaction models. CANopen uses the CAN bus as the data link
layer. Every CANopen communication object is mapped to one or more CAN frames.
The CAN identifier of those frames is called the COB-ID (communication object
identifier). In the CAN base frame format the COB-ID is 11 bits wide.

A CANopen network consists of one NMT master and up to 127 NMT slaves. Each
node has a Node-ID in the range 1..127. Node-ID 0 is reserved to address all
nodes (broadcast) in some services.


5  Object dictionary

The object dictionary (OD) is the heart of a CANopen device. It is a grouped
list of all the data items (objects) that influence the behaviour of the
application objects, the communication objects, and the state machine.

5.1  Addressing

Each object in the dictionary is addressed using a 16-bit index and an 8-bit
sub-index. The index identifies the object; the sub-index identifies a
component of a complex object (record or array). A simple VAR object uses
sub-index 0 only. For an ARRAY or RECORD, sub-index 0 holds the highest
sub-index supported (the number of entries).

5.2  Object dictionary layout

   Index range        Description
   0x0000             reserved
   0x0001 - 0x009F    data types
   0x00A0 - 0x0FFF    reserved
   0x1000 - 0x1FFF    communication profile area (CiA 301)
   0x2000 - 0x5FFF    manufacturer-specific profile area
   0x6000 - 0x9FFF    standardised device profile area (CiA 401/402/...)
   0xA000 - 0xBFFF    standardised interface profile area
   0xC000 - 0xFFFF    reserved

5.3  Mandatory and standardised communication-profile entries

   Index   Object       Name / meaning
   0x1000  VAR          Device type
   0x1001  VAR          Error register
   0x1003  ARRAY        Pre-defined error field (EMCY history)
   0x1005  VAR          COB-ID SYNC message
   0x1006  VAR          Communication cycle period
   0x1008  VAR          Manufacturer device name
   0x100A  VAR          Manufacturer software version
   0x100C  VAR          Guard time
   0x100D  VAR          Life time factor
   0x1010  ARRAY        Store parameters
   0x1011  ARRAY        Restore default parameters
   0x1012  VAR          COB-ID time stamp object (TIME)
   0x1014  VAR          COB-ID emergency message (EMCY)
   0x1015  VAR          Inhibit time EMCY
   0x1016  ARRAY        Consumer heartbeat time
   0x1017  VAR          Producer heartbeat time
   0x1018  RECORD       Identity object (vendor-ID, product code,
                        revision number, serial number)
   0x1200  RECORD       SDO server parameter
   0x1280  RECORD       SDO client parameter
   0x1400  RECORD       RPDO communication parameter (first RPDO)
   0x1600  RECORD       RPDO mapping parameter (first RPDO)
   0x1800  RECORD       TPDO communication parameter (first TPDO)
   0x1A00  RECORD       TPDO mapping parameter (first TPDO)

The Device type object 0x1000 (mandatory) is a 32-bit value: the lower 16 bits
hold the device profile number (for example 401 for generic I/O, 402 for
drives) and the upper 16 bits hold additional information.

The Identity object 0x1018 (mandatory) is a RECORD with sub-index 1 vendor-ID
(assigned by CiA), sub-index 2 product code, sub-index 3 revision number, and
sub-index 4 serial number.

The Error register object 0x1001 (mandatory) is a single byte whose bits flag
generic, current, voltage, temperature, communication, device-profile-specific
and manufacturer-specific error classes.


6  Communication objects

CANopen defines the following communication objects, each carried by CAN frames
whose CAN identifier is the COB-ID:

   - PDO  : process data object (real-time data exchange)
   - SDO  : service data object (object-dictionary access)
   - NMT  : network management (state control, error control)
   - SYNC : synchronisation object
   - TIME : time-stamp object
   - EMCY : emergency object
   - Heartbeat / Node guarding (error control)


6.1  Process Data Object (PDO)

A PDO transfers process data in real time. It carries up to 8 data bytes (one
CAN data frame) with no protocol overhead beyond the COB-ID. PDOs follow the
producer/consumer model: one producer broadcasts, any number of consumers
receive.

There are two kinds of PDO from the point of view of a device:
   - Transmit-PDO (TPDO): the device produces (transmits) the PDO.
   - Receive-PDO (RPDO): the device consumes (receives) the PDO.

PDO communication parameters (0x1400 for the first RPDO, 0x1800 for the first
TPDO) define:
   - the COB-ID used by the PDO,
   - the transmission type,
   - the inhibit time (minimum gap between two TPDOs),
   - the event timer,
   - the SYNC start value.

PDO mapping parameters (0x1600 for the first RPDO, 0x1A00 for the first TPDO)
define which object-dictionary entries are packed into the PDO and in which
order. Sub-index 0 of a mapping object holds the number of mapped objects;
each further sub-index holds a 32-bit mapping entry: index (16 bit), sub-index
(8 bit), and length in bits (8 bit).

Transmission types:
   0          synchronous, acyclic (transmitted on the next SYNC after a change)
   1..240     synchronous, cyclic (transmitted every n-th SYNC)
   241..251   reserved
   252        synchronous, RTR-only
   253        asynchronous, RTR-only
   254        asynchronous, manufacturer-specific event
   255        asynchronous, device-profile-specific event

A synchronous PDO is sampled and/or actuated in relation to the SYNC object.
An asynchronous (event-driven) PDO is transmitted when an application event
occurs, or on the event timer expiry.


6.2  Service Data Object (SDO)

An SDO provides access to the entries of a device's object dictionary. It uses
the client/server communication model: the SDO client (typically the NMT master
or a configuration tool) reads (upload) or writes (download) an entry in the
SDO server's object dictionary, addressing it by index and sub-index.

An SDO uses two COB-IDs: one for client-to-server and one for server-to-client.
For the default server SDO of a device with Node-ID, the request COB-ID is
0x600 + Node-ID and the response COB-ID is 0x580 + Node-ID.

SDO transfer protocols:
   - Expedited transfer  : up to 4 data bytes carried directly in the single
                           request/response frame (the fast common case).
   - Segmented transfer  : data larger than 4 bytes is split into 7-byte
                           segments with a toggle bit per segment.
   - Block transfer      : optional high-throughput mode that transfers a
                           sequence of segments before a single acknowledge.

An SDO transfer that fails is terminated by an SDO abort transfer message
carrying a 32-bit abort code (for example 0x06020000 object does not exist,
0x06090011 sub-index does not exist, 0x08000000 general error).


6.3  Network Management (NMT)

NMT follows the master/slave model. Exactly one NMT master controls the NMT
state machine of every NMT slave. The NMT state machine of a CANopen device
has the following states:

   Initialisation     entered automatically after power-on or reset; the
                      device initialises and then transmits the boot-up
                      message and enters Pre-operational.
   Pre-operational    SDO and NMT communication are allowed; PDOs are NOT
                      exchanged. Reached automatically after boot-up.
   Operational        all communication objects are active, including PDOs.
   Stopped            only NMT and the error-control objects (heartbeat /
                      node guarding) are allowed; SDOs and PDOs are stopped.

NMT module-control (state-change) commands are sent by the NMT master in a
2-byte CAN frame with COB-ID 0 (the highest CAN priority). Byte 0 is the
command specifier (CS); byte 1 is the addressed Node-ID (0 = all nodes):

   CS = 0x01   Start remote node       -> Operational
   CS = 0x02   Stop remote node        -> Stopped
   CS = 0x80   Enter pre-operational   -> Pre-operational
   CS = 0x81   Reset node              -> Initialisation (reset application)
   CS = 0x82   Reset communication     -> Initialisation (reset communication)

After Initialisation the device sends a boot-up message (COB-ID 0x700 +
Node-ID, one data byte = 0x00) to announce that it has entered Pre-operational.


6.4  SYNC object

The SYNC object is broadcast periodically by the SYNC producer to provide a
network-wide synchronisation signal. Synchronous PDOs are sampled / actuated
relative to the SYNC. The SYNC has the default COB-ID 0x080 and carries no data
(or an optional 1-byte counter). The communication cycle period (object 0x1006)
defines the SYNC interval.


6.5  TIME object

The TIME-stamp object distributes a common network time. It uses the default
COB-ID 0x100 and carries a 6-byte TIME_OF_DAY value (milliseconds since
midnight plus days since 1 January 1984).


6.6  Emergency object (EMCY)

When an internal error occurs in a device, it transmits an emergency (EMCY)
object exactly once per error event. The EMCY message carries an 8-byte payload:
a 16-bit emergency error code, the 8-bit error register (object 0x1001), and 5
bytes of manufacturer-specific error information. The default EMCY COB-ID is
0x080 + Node-ID. Pre-defined error codes include 0x0000 error reset / no error,
0x1000 generic error, 0x2000 current, 0x3000 voltage, 0x4000 temperature,
0x5000 device hardware, 0x6000 device software, 0x8100 communication, and
0x8110 CAN overrun.


6.7  Error control: heartbeat and node guarding

CANopen provides two mutually exclusive error-control mechanisms:

   Heartbeat       The heartbeat producer cyclically transmits a heartbeat
                   message (COB-ID 0x700 + Node-ID, one data byte = the NMT
                   state: 0x00 boot-up, 0x04 stopped, 0x05 operational, 0x7F
                   pre-operational). One or more heartbeat consumers monitor it
                   against the consumer heartbeat time (object 0x1016). The
                   producer heartbeat time is object 0x1017.

   Node guarding / life guarding
                   The NMT master polls each slave with a remote-transmission-
                   request guarding frame; the slave answers with its NMT state
                   and a toggle bit. The guard time (object 0x100C) and the life
                   time factor (object 0x100D) define the life-guarding timeout.

A device implements either heartbeat or node guarding, not both at once.


7  Predefined connection set (default COB-ID allocation)

To make a network operable without configuration, CANopen defines a default
COB-ID allocation as a function of the Node-ID. With an 11-bit CAN identifier,
the four high bits form the function code and the seven low bits hold the
Node-ID (COB-ID = function-code * 0x80 + Node-ID):

   Object                 Function code   Default COB-ID range
   NMT module control     0000            0x000             (broadcast)
   SYNC                    -              0x080             (broadcast)
   EMCY                   0001            0x081 - 0x0FF
   TIME                    -              0x100             (broadcast)
   TPDO1 (transmit)       0011            0x181 - 0x1FF
   RPDO1 (receive)        0100            0x201 - 0x27F
   TPDO2 (transmit)       0101            0x281 - 0x2FF
   RPDO2 (receive)        0110            0x301 - 0x37F
   TPDO3 (transmit)       0111            0x381 - 0x3FF
   RPDO3 (receive)        1000            0x401 - 0x47F
   TPDO4 (transmit)       1001            0x481 - 0x4FF
   RPDO4 (receive)        1010            0x501 - 0x57F
   SDO (server -> client) 1011            0x581 - 0x5FF
   SDO (client -> server) 1100            0x601 - 0x67F
   NMT error control      1110            0x701 - 0x77F
                          (heartbeat / node guarding / boot-up)

This default mapping means a freshly powered node with a known Node-ID can
immediately be addressed by its SDO, send its boot-up message, and produce its
default PDOs without any prior configuration.


8  Electronic data sheet (EDS) and device configuration file (DCF)

The Electronic Data Sheet (EDS, CiA 306) is a standardised text file (INI-style)
that describes all object-dictionary entries a device supports: index,
sub-index, data type, access type, default value, and PDO-mappability. The EDS
describes a device type; it is independent of any single physical node.

A Device Configuration File (DCF) is an EDS that has been filled in with the
actual parameter values and the actual Node-ID for one concrete device on one
concrete network. Configuration tools use EDS/DCF files to set up a CANopen
network.


9  Layer setting services (LSS)

Layer Setting Services (CiA 305) allow a configuration tool to inquire and
change the Node-ID and the bit-timing (baud rate) of a node over the CAN bus,
even when several nodes initially share the default (unconfigured) Node-ID. LSS
selects a single node by its 128-bit LSS address (the four entries of the
identity object 0x1018) and then assigns it a Node-ID.


10  Data types

CANopen defines basic data types (BOOLEAN, INTEGER8/16/32, UNSIGNED8/16/32,
REAL32, VISIBLE_STRING, OCTET_STRING, TIME_OF_DAY, TIME_DIFFERENCE) and complex
data types (PDO_COMMUNICATION_PARAMETER, PDO_MAPPING, SDO_PARAMETER, IDENTITY).
These are listed in the object dictionary at indices 0x0001..0x009F and form the
basis for every object-dictionary entry's data-type attribute.


11  Device profiles

A CANopen device profile standardises the application objects (indices
0x6000..0x9FFF) of a class of devices so that products from different vendors
interoperate:

   CiA 401   generic I/O modules (digital and analogue inputs and outputs)
   CiA 402   drives and motion control (servo, stepper, frequency inverter)
   CiA 404   measuring devices and closed-loop controllers
   CiA 406   encoders
   CiA 408   fluid power technology

A device declares its profile number in the lower 16 bits of the device type
object 0x1000.


12  Relationship to CAN

CANopen is strictly an application layer ABOVE the CAN data link layer. The CAN
frame format, the CAN arbitration by identifier, the CAN bit-stuffing, the CAN
acknowledge slot, and the CAN error frame / error handling are all defined by
the CAN standard (ISO 11898) and are used unchanged by CANopen. CANopen adds:
the object dictionary, the COB-ID assignment, the PDO/SDO/NMT/SYNC/TIME/EMCY
communication objects, the NMT boot-up state machine, heartbeat/node guarding,
and the EDS/DCF device-description files. A plain CAN controller that only
generates and receives raw CAN frames, with no object dictionary and no PDO/SDO/
NMT, is NOT a CANopen device.


13  Summary of mandatory CANopen requirements

   - 16-bit index plus 8-bit sub-index object dictionary.
   - Object 0x1000 device type and 0x1018 identity object (mandatory).
   - Object 0x1001 error register (mandatory).
   - At least one SDO server (default 0x600+Node-ID / 0x580+Node-ID).
   - The NMT slave state machine: Initialisation -> Pre-operational ->
     Operational <-> Stopped, driven by NMT module-control commands.
   - The boot-up message after Initialisation.
   - One error-control mechanism: heartbeat or node guarding.
   - Node-ID in the range 1..127 and the predefined connection set so the
     device is operable with its default COB-IDs.
