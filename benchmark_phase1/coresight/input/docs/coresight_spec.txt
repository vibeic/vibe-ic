ARM CoreSight On-Chip Debug and Trace Architecture
Specification Overview (spec-grounded, public-architecture level)

NOTE ON SOURCING. This document describes the ARM CoreSight debug and trace
architecture at the level that is publicly documented in the ARM Architecture
Reference Manual, public CoreSight Technical Reference Manuals (TRMs), and ARM
public application notes. The full CoreSight Architecture Specification and the
individual component TRMs are ARM proprietary documents. This overview
therefore describes documented BEHAVIOR, component roles, register names, and
architectural relationships only. It invents NO exact numeric timing,
electrical, or area values; where a quantity is implementation-defined that is
stated explicitly rather than guessed.

1. SCOPE AND PURPOSE

CoreSight is ARM's on-chip debug and trace framework. It is the architecture
that ties together the debug access path, the trace generation sources, the
trace transport, the trace capture sinks, and the cross-trigger fabric of a
System-on-Chip. CoreSight is NOT itself a wire-level transport such as JTAG or
Serial Wire Debug (SWD); rather it is the architecture that SITS ON TOP of a
JTAG or SWD transport and turns a chip into a debuggable, traceable system.
A CoreSight system is discoverable: an external debugger walks a hierarchy of
ROM Tables and reads each component's identification registers to enumerate the
debug and trace components present on the device.

A complete CoreSight subsystem is built from the following classes of block:
  - A Debug Access Port (DAP) providing memory-mapped access to the on-chip
    debug bus from an external debugger.
  - Trace sources (ETM, PTM, ITM, STM) that generate trace.
  - A trace transport built on the AMBA Trace Bus (ATB), with funnels that
    combine streams and replicators that fan streams out.
  - Trace sinks (TPIU, ETB, ETF, ETR) that take trace off-chip or into memory.
  - A Cross Trigger fabric (CTI per component plus a Cross Trigger Matrix CTM)
    that distributes debug events such as halt and restart across cores.
  - ROM Tables and component identification registers for discovery.
  - Debug authentication signals that gate invasive and non-invasive debug.

2. DEBUG ACCESS PORT (DAP)

The Debug Access Port (DAP) is the entry point for an external debugger into
the on-chip debug infrastructure. The DAP is defined by the ARM Debug Interface
(ADI, ADIv5/ADIv6). The DAP is composed of exactly two kinds of element:

2.1 Debug Port (DP). The Debug Port is the external-facing element of the DAP.
It terminates the physical debug transport and converts it into accesses on the
internal DAP bus. There are two Debug Port variants:
  - SW-DP: a Serial Wire Debug Port. The external transport is the two-wire
    Serial Wire interface (SWDIO bidirectional data, SWCLK clock). The Serial
    Wire protocol carries packet requests and ACK/WAIT/FAULT responses.
  - JTAG-DP: a JTAG Debug Port. The external transport is the IEEE 1149.1 JTAG
    TAP (TCK, TMS, TDI, TDO, optional TRSTn) driving a TAP state machine, with
    an instruction register selecting DPACC/APACC scan chains.
  - SWJ-DP: a combined Serial Wire / JTAG Debug Port that allows the external
    pins to be switched between SWD and JTAG operation.
The Debug Port owns the DP registers: IDCODE/DPIDR, CTRL/STAT (power-up and
status: CDBGPWRUPREQ/ACK, CSYSPWRUPREQ/ACK, sticky error flags), SELECT (selects
the active Access Port and the addressed register bank), and the RDBUFF read
buffer. The DP performs the power-up handshake that brings the debug power
domain and the system power domain up before any access proceeds.

2.2 Access Ports (AP). An Access Port bridges from the DAP internal bus onto an
on-chip bus so the debugger can perform memory-mapped reads and writes of the
debug components and of system memory. The architected Access Ports are:
  - MEM-AP generically; concretely realized as:
  - AHB-AP: a Memory Access Port that masters an AMBA AHB bus (typically used to
    reach system memory and memory-mapped peripherals as the core would see
    them).
  - APB-AP: a Memory Access Port that masters an AMBA APB bus. The Debug APB is
    the dedicated low-bandwidth interconnect on which the CoreSight debug
    registers of every component are memory-mapped; APB-AP is how the debugger
    reaches the debug register space of the cores and CoreSight components.
  - AXI-AP: a Memory Access Port that masters an AMBA AXI bus for high-throughput
    access to system memory.
  - JTAG-AP: an Access Port that masters a legacy JTAG scan chain behind the DAP.
Each MEM-AP exposes the architected registers CSW (control/status word: size,
auto-increment, access mode), TAR (Transfer Address Register), DRW (Data
Read/Write), the banked Banked Data Registers BD0-BD3, the configuration
register CFG, the debug base address register BASE (which points at the first
ROM Table), and the AP identification register IDR.

2.3 The Debug APB. CoreSight debug registers live in a memory-mapped debug
register space reached over an APB interconnect, conventionally called the Debug
APB. Each CoreSight component occupies a 4 KB block of this debug register space.
The debugger reaches a component's registers by programming the MEM-AP TAR with
the component's base address (discovered from the ROM Table) and reading/writing
through DRW. Access to the debug register space is gated by the debug
authentication signals (see section 9).

3. TRACE SOURCES

A trace source generates a trace stream and emits it onto the AMBA Trace Bus.
The architected CoreSight trace sources are:

3.1 ETM (Embedded Trace Macrocell), including ETMv4 (the ETMv4 architecture is
also called the ETM architecture used by modern cores). An ETM observes a
processor and produces instruction trace (program flow: branches taken, the
addresses of indirect branches and exceptions) and optionally data trace
(addresses and/or values of load/store accesses). ETM trace is highly
compressed: the decoder reconstructs full program flow from a small number of
trace bytes plus the program image. An ETM is configured through its CoreSight
debug registers (trace enable, address-range comparators, context-ID
comparators, counters, sequencer, and the ATB trace ID register TRCTRACEIDR).

3.2 PTM (Program Trace Macrocell). A program-flow-only trace source used by some
ARM cores; like the ETM it emits instruction (program-flow) trace onto the ATB.

3.3 ITM (Instrumentation Trace Macrocell). A software-driven trace source. Code
writes to ITM stimulus port registers and the ITM emits the written values as
trace packets onto the ATB. The ITM is used for printf-style instrumentation and
for timestamp generation.

3.4 STM (System Trace Macrocell). A system-wide instrumentation trace source
defined by the MIPI System Trace Protocol (STP). The STM exposes a large set of
memory-mapped stimulus ports so that many software masters can emit trace
concurrently; each write becomes an STP packet emitted onto the ATB.

Every trace source carries an ATB trace ID (a small identifier in the
TRACEIDR/TRCTRACEIDR register) so that the captured, merged trace stream can be
demultiplexed back into per-source streams by the decoder.

4. TRACE TRANSPORT: AMBA TRACE BUS (ATB), FUNNEL, REPLICATOR

4.1 ATB. Trace data flows between CoreSight components on the AMBA Trace Bus
(ATB), an AMBA point-to-point trace interconnect. An ATB link carries the trace
data (ATDATA), the trace ID (ATID), a byte-count/valid (ATVALID/ATBYTES), and a
ready/back-pressure handshake (ATREADY), plus flush (AFVALID/AFREADY) signaling.
Back-pressure on the ATB stalls upstream sources when a downstream sink cannot
accept data.

4.2 Trace Funnel. A CoreSight Trace Funnel (also CSTF) combines several ATB input
streams into one ATB output stream. The funnel arbitrates between its enabled
input ports (priority programmable through the funnel's control register) and
interleaves the trace, preserving each source's ATB trace ID so the streams can
later be separated.

4.3 Trace Replicator. A CoreSight Trace Replicator (also CSTR) fans one ATB input
stream out to two ATB output streams, for example to send the same trace to both
an on-chip buffer (ETB/ETF) and an off-chip port (TPIU) simultaneously. Each
replicator output has an ID-filter so a given output only forwards the trace IDs
of interest.

5. TRACE SINKS

A trace sink terminates a trace stream. The architected CoreSight trace sinks
are:

5.1 TPIU (Trace Port Interface Unit). The TPIU formats the on-chip ATB trace and
drives it off-chip on a parallel trace port (the Trace Port: a trace clock
TRACECLK plus trace data lines TRACEDATA[n], typically 1/2/4/8/16 data lines)
or, on a Serial Wire system, onto the Serial Wire Output (SWO) single pin. The
TPIU applies the trace-port framing/formatter so the external Trace Port
Analyzer can recover the interleaved trace and split it by trace ID.

5.2 ETB (Embedded Trace Buffer). An on-chip circular RAM that captures the ATB
trace stream when no off-chip trace port is available or affordable. The
debugger drains the ETB over the Debug APB after the capture window.

5.3 ETF (Embedded Trace FIFO). A configurable on-chip RAM (the CoreSight Trace
Memory Controller in FIFO mode) used either as a circular buffer (like an ETB)
or as a FIFO that smooths bursty trace before a slower downstream sink.

5.4 ETR (Embedded Trace Router). The CoreSight Trace Memory Controller in router
mode. The ETR is itself an AXI master: it writes the captured trace into general
system memory (DRAM) through an AXI interface, using a scatter-gather page table,
so the trace buffer can be very large and shared with the operating system.

6. CROSS TRIGGER: CTI AND CTM

CoreSight distributes debug events across the components of the system with a
cross-trigger fabric:

6.1 CTI (Cross Trigger Interface). Each core (and many other components) has a
Cross Trigger Interface. A CTI maps a component's local trigger inputs and
trigger outputs (for example: a processor halt request, a processor restart
request, an ETM trigger, a PMU overflow) onto a set of channels. The CTI is
programmed through its CoreSight registers: the channel-in / channel-out enable
registers (CTIINEN, CTIOUTEN), the application-trigger registers (CTIAPPSET,
CTIAPPCLEAR, CTIAPPPULSE), and the gate register CTIGATE.

6.2 CTM (Cross Trigger Matrix). The Cross Trigger Matrix is the channel
broadcast fabric that connects the CTIs together. An event raised on a channel by
one CTI is broadcast over the CTM to every CTI that is listening on that channel,
which then drives the mapped local trigger output. This is how, for example, a
breakpoint on one core can be made to halt all the other cores synchronously
(synchronous halt), and a single restart can release them together.

7. DISCOVERY: ROM TABLES AND COMPONENT IDENTIFICATION

7.1 ROM Table. A CoreSight system is self-describing through a hierarchy of ROM
Tables. The MEM-AP BASE register points at the top-level ROM Table. A ROM Table
is a CoreSight component whose body is a list of entry registers; each entry
holds a relative address offset to another component (or to a nested ROM Table)
and a present bit. By walking the ROM Table tree and reading the offsets, a
debugger discovers every debug and trace component on the device and the base
address of each one's 4 KB register block.

7.2 Component and Peripheral Identification Registers. Every CoreSight component
implements a standard block of identification registers in the top of its 4 KB
register space. These are:
  - The Component ID registers CIDR0-CIDR3 (a fixed preamble plus a class field
    that says, for example, ROM Table vs CoreSight component vs generic IP).
  - The Peripheral ID registers PIDR0-PIDR7 (part number, JEP106 designer/
    continuation code, revision, and a 4 KB-count field for multi-block
    components).
  - The architecture/type registers DEVARCH (the architected register that names
    the component's architecture, present from CoreSight architecture v3) and
    DEVTYPE (a major/sub classification: trace source, trace sink, trace link,
    debug control, cross-trigger, etc.).
A debugger uses CIDR/PIDR/DEVARCH/DEVTYPE to positively identify each component
it finds while walking the ROM Table, rather than relying on the ROM Table
offsets alone.

8. CLAIM, LOCK, AND POWER/STATUS MANAGEMENT REGISTERS

In addition to the identification registers, CoreSight components share a set of
management registers near the top of their register block:
  - CLAIMSET / CLAIMCLR: claim-tag bits that let multiple debug agents (an
    external debugger and on-target self-hosted debug) cooperate without
    clobbering each other.
  - LAR (Lock Access Register) / LSR (Lock Status Register): a software lock that
    must be unlocked (by writing the lock key) before the component's registers
    can be modified from memory-mapped accesses.
  - AUTHSTATUS: reports the current debug authentication permissions for the
    component (see section 9).
  - DEVID / DEVAFF: device configuration and affinity (which processor a
    component is associated with).

9. DEBUG AUTHENTICATION

Invasive and non-invasive debug, at both the Non-secure and Secure security
states, are individually gated by authentication signals presented to each
debug/trace component:
  - DBGEN: invasive debug enable (Non-secure). Allows halting-mode debug.
  - NIDEN: non-invasive debug enable (Non-secure). Allows trace and the PMU.
  - SPIDEN: Secure invasive debug enable. Allows invasive debug of Secure state.
  - SPNIDEN: Secure non-invasive debug enable. Allows trace of Secure state.
The AUTHSTATUS register of each component reflects which of these are currently
permitted. A production device typically deasserts the Secure (and possibly all)
authentication signals so that an attacker cannot use the debug architecture to
read Secure assets; a development device asserts them. These signals are the
architectural hook by which a chip's security/lifecycle controller enables or
disables debug.

10. PUTTING IT TOGETHER: A TYPICAL TRACE SESSION

A representative debug-and-trace bring-up over CoreSight proceeds as follows:
  1. The debugger connects over the physical transport (SWD or JTAG) to the
     Debug Port (SW-DP or JTAG-DP) of the DAP.
  2. The DP performs the debug/system power-up handshake (CDBGPWRUPREQ/ACK,
     CSYSPWRUPREQ/ACK) so the debug logic is powered and clocked.
  3. The debugger selects the APB-AP, reads the MEM-AP BASE register to find the
     top-level ROM Table, and walks the ROM Table tree, reading CIDR/PIDR/
     DEVARCH/DEVTYPE at each entry to enumerate the cores, ETMs, ITM/STM, funnel,
     replicator, CTIs, TPIU/ETB/ETF/ETR present.
  4. The debugger unlocks (LAR), claims (CLAIMSET), and programs each trace
     source (ETM/ITM/STM) with its ATB trace ID and trace-enable configuration.
  5. The debugger programs the funnel (enable the relevant input ports) and the
     replicator (route trace to the chosen sink) and configures the sink
     (TPIU formatter / ETB-ETF buffer / ETR AXI scatter-gather buffer).
  6. The debugger programs the CTIs (channel mappings) and the CTM so that, e.g.,
     a halt on any core halts all cores.
  7. Trace is captured (off-chip via TPIU/SWO, or on-chip into ETB/ETF, or into
     DRAM via ETR over AXI), then drained and decoded off-line. The decoder uses
     the per-source ATB trace IDs to demultiplex the merged stream and the
     program image to reconstruct ETM program flow.

11. RELATIONSHIP TO, AND DISTINCTION FROM, JTAG AND SWD

CoreSight is deliberately layered above the JTAG and SWD transports and must not
be confused with them:
  - JTAG (IEEE 1149.1) is a boundary-scan / test-access transport: a TAP state
    machine driven by TCK/TMS/TDI/TDO with an instruction register and data
    registers. A pure JTAG document with only the TAP state machine, boundary
    scan, BYPASS/IDCODE/EXTEST instructions, and no DAP/AP, no ATB, no funnel,
    no trace source/sink, and no ROM-table discovery is NOT a CoreSight document.
  - SWD (Serial Wire Debug) is the two-wire ADIv5 Debug Port transport (SWDIO,
    SWCLK) with packet request / ACK / data phases and the DP CTRL/STAT and
    SELECT registers. A pure SWD/ADIv5 Debug-Port document with only the
    serial-wire line protocol and DP registers, and no Access Ports onto a debug
    bus, no trace architecture (no ATB/funnel/replicator/ETM/ETB/TPIU), and no
    ROM-table component discovery is NOT a CoreSight document either.
CoreSight is precisely the architecture that ADDS, on top of such a transport,
the DAP-with-Access-Ports memory-mapped debug bus, the ATB trace transport with
funnels and replicators, the ETM/PTM/ITM/STM trace sources, the TPIU/ETB/ETF/ETR
trace sinks, the CTI/CTM cross-trigger fabric, and the ROM-table / component-ID
discovery mechanism. The presence of those structural elements is what makes a
document a CoreSight document.

12. VERSIONING NOTE

CoreSight has evolved across architecture generations (commonly referred to as
CoreSight v1/v2/v3 in public material). Later generations add the DEVARCH
register (architecture identification), refine the component identification
scheme, and extend the trace and cross-trigger components (for example ETMv4 and
the CoreSight Trace Memory Controller realizing ETF/ETR). The DAP itself follows
the ARM Debug Interface versions ADIv5 and ADIv6. Exact register bit layouts,
the number of stimulus ports on an STM, the depth of an ETB/ETF, the number of
TPIU trace-data pins, and the number of CTM channels are all
implementation-defined and are not fixed by this overview.
