PROFINET
PROFINET IO — Industrial Ethernet Communication Specification
Based on IEC 61158 (Type 10) and IEC 61784-2 (Communication Profile Family 3, CPF 3)

PI (PROFIBUS & PROFINET International)
PROFINET System Description — Technology and Application


===============================================================================
1. OVERVIEW
===============================================================================

PROFINET is the open Industrial Ethernet standard for automation, standardized
in IEC 61158 (Type 10) and IEC 61784-2 (Communication Profile Family 3). It is
maintained by PI (PROFIBUS & PROFINET International). PROFINET runs on standard
100 Mbit/s and 1 Gbit/s switched Ethernet using standard IEEE 802.3 Ethernet
frames and standard Ethernet hardware (cables, connectors, PHYs, switches).

PROFINET is NOT a separate physical layer: it re-uses Fast Ethernet / Gigabit
Ethernet at the physical and MAC layers. What PROFINET adds is the
application-protocol layer for real-time cyclic process data exchange between
distributed field devices and controllers, the device model, the engineering
and address-assignment protocols, and real-time scheduling on top of Ethernet.

PROFINET defines THREE performance / real-time classes that share the same
device model and engineering but use different transport handling:

  - NRT  (Non-Real-Time)            : standard TCP/IP and UDP/IP communication,
                                      used for parameterization, configuration,
                                      diagnosis, and acyclic services. Not time
                                      critical.
  - RT   (Real-Time)                : prioritized Layer-2 communication. Cyclic
                                      process data is sent in standard Ethernet
                                      frames with EtherType 0x8892, bypassing
                                      the TCP/IP stack, and prioritized using
                                      the VLAN tag PCP (priority 6).
  - IRT  (Isochronous Real-Time)    : hardware-scheduled, bandwidth-reserved,
                                      clock-synchronized transmission for
                                      motion-control class applications. Uses a
                                      sync domain and time-slotting of the
                                      send cycle into a reserved (red) phase for
                                      IRT frames and an open (green) phase for
                                      RT/NRT traffic.

PROFINET IO is the part of PROFINET that describes cyclic and acyclic data
exchange with distributed field I/O. (PROFINET CBA, the older
component-based-automation variant, is deprecated and not covered here.)


===============================================================================
2. ETHERNET BASE LAYER
===============================================================================

Physical / MAC base:
  - 100BASE-TX (Fast Ethernet) and 1000BASE-T (Gigabit Ethernet), full duplex,
    switched. Standard IEEE 802.3 framing: preamble, SFD, destination MAC,
    source MAC, EtherType/length, payload, FCS (CRC-32).
  - Standard 6-byte MAC addresses; standard Ethernet switching.
  - 100 Mbit/s is the baseline; PROFINET devices use auto-negotiation but
    typically run at fixed 100 Mbit/s full-duplex for deterministic behavior.

EtherType usage:
  - 0x8892  PROFINET Real-Time (RT/IRT) frames (also called the PNIO/PN-RT
            EtherType). Cyclic and acyclic real-time frames ride directly on
            Layer 2 with this EtherType, NOT inside IP.
  - 0x8100  IEEE 802.1Q VLAN tag, carrying the 3-bit PCP priority field. RT
            cyclic data uses PCP = 6 (high priority); other classes use lower
            priorities.
  - 0x0800  IPv4, used for NRT (TCP/IP, UDP/IP) services.
  - 0x0806  ARP.
  - 0x8035  RARP.
  - 0x88CC  LLDP (Link Layer Discovery Protocol), used by PROFINET for
            topology discovery and neighbor detection.

The PROFINET RT frame carried in EtherType 0x8892 contains:
  - FrameID         (2 bytes) : identifies the frame class / connection. Ranges:
                                0x0100-0x0FFF IRT cyclic (high performance),
                                0x8000-0xBFFF RT cyclic class 1/2,
                                0xFC00-0xFCFF DCP, 0xFE00-0xFEFF reserved /
                                acyclic (Alarm low/high), 0xFF80-0xFF8F PTCP.
  - Data            (n bytes) : the cyclic IO data (IO-CR payload) made of
                                IO Data Objects with their IOPS, plus the
                                consumer-status IOCS bytes.
  - APDU Status     : appended after the cyclic data:
                        Cycle Counter (2 bytes), Data Status (1 byte),
                        Transfer Status (1 byte).
  - The frame ends with the standard Ethernet FCS.

Frame size: standard Ethernet payload 46..1500 bytes; PROFINET RT frames fit
within the standard MTU (no jumbo frames required).


===============================================================================
3. DEVICE MODEL AND ROLES
===============================================================================

PROFINET IO defines three device roles:

  - IO-Controller : typically a PLC (programmable logic controller). It runs
                    the automation program, establishes the Application
                    Relation(s) to the IO-Devices, sends cyclic output data
                    (provider) and consumes cyclic input data (consumer), and
                    handles alarms. There is one primary IO-Controller per AR
                    (a shared-device case may add further controllers).

  - IO-Device     : a distributed field device (remote I/O block, drive,
                    sensor/actuator station, valve terminal). It provides input
                    process data to and consumes output process data from the
                    IO-Controller. Its physical/logical structure is described
                    by slots and subslots.

  - IO-Supervisor : an engineering / commissioning / diagnostic station
                    (engineering PC, HMI, programming device). It can read and
                    write parameters and diagnosis acyclically and is used for
                    commissioning, not for the cyclic control loop.

Device structure — Slot / Subslot model:
  - A modular IO-Device is organized into SLOTS (physical or logical module
    positions). Each slot contains SUBSLOTS (sub-modules) that carry the actual
    I/O channels.
  - The Device Access Point (DAP) is always slot 0; it represents the device /
    interface itself (the Ethernet interface and ports are addressed via
    subslots of slot 0, e.g. 0x8000 interface, 0x8001 port 1, 0x8002 port 2).
  - Each (slot, subslot) has a Module Ident Number and Submodule Ident Number
    that the configured (expected) topology in the engineering tool must match
    the real (plugged) modules; mismatches raise diagnosis.

GSDML (General Station Description Markup Language):
  - Each IO-Device ships with a GSD file in the GSDML XML format
    (GSDML-DeviceProfile). It describes the device identity (VendorID,
    DeviceID), the available modules/submodules, their I/O data sizes,
    parameters, supported features (RT/IRT, conformance class, MRP), and
    diagnosis texts.
  - The engineering tool imports the GSDML, the integrator assembles the
    expected configuration (slots/subslots/modules), and downloads it to the
    IO-Controller. GSDML is the PROFINET counterpart of PROFIBUS GSD, but it is
    an XML schema (NOT the keyword-based PROFIBUS GSD text format).


===============================================================================
4. ADDRESSING AND DISCOVERY — DCP
===============================================================================

Every PROFINET IO-Device needs a station name (NameOfStation) and an IP
configuration before cyclic communication can start. PROFINET uses names, not
fixed IP addresses, as the primary device identity — the name is the key for
the AR establishment.

DCP — Discovery and Configuration Protocol:
  - A Layer-2 protocol (carried in EtherType 0x8892, FrameID 0xFEFE/0xFEFD/
    0xFEFC range, the DCP FrameIDs) used to discover devices, read/assign the
    station name, and assign the IP address (IP, subnet mask, gateway).
  - DCP services: Identify (find all stations / a station by name), Get
    (read a parameter), Set (assign NameOfStation, assign IP), Hello
    (device announces itself after power-up). DCP-Identify is typically a
    multicast request; the device answers with its current name and address.
  - The IO-Supervisor or IO-Controller uses DCP-Set to commission a device
    name; the device stores the name in non-volatile memory.
  - DCP is the standard mechanism; DHCP is optional. Flashing/blinking (a DCP
    Signal service driving the device LED) lets an engineer physically locate a
    station found by DCP.

LLDP (IEC 61158 / IEEE 802.1AB) is used additionally for neighborhood/topology
detection: each port periodically sends LLDP frames (EtherType 0x88CC) with the
port ID and chassis ID, so the engineering tool can build the physical topology
and support topology-based name assignment and cable-swap detection.


===============================================================================
5. CONNECTION MODEL — APPLICATION RELATION (AR) AND COMMUNICATION RELATIONS (CR)
===============================================================================

Application Relation (AR):
  - The logical connection between an IO-Controller and an IO-Device. It is
    established once at start-up and groups all the Communication Relations.
  - AR establishment uses the acyclic CL-RPC (Connect service) over UDP: the
    IO-Controller sends a Connect.req carrying the expected configuration
    (modules/submodules, IO-CR parameters, send clock, reduction ratio, watchdog
    factor), and the IO-Device answers Connect.res. This is the "Connect"
    handshake.
  - AR types include the IO-AR (the normal controller<->device relation),
    the Supervisor-AR / DeviceAccess-AR (read/write only, used by an
    IO-Supervisor), and Implicit-AR (read record without a full AR).

Communication Relations (CR) within an AR:
  - IO-CR (Input/Output Communication Relation) : the cyclic data channel.
    There is normally one Input-CR (device -> controller, the provider on the
    device side) and one Output-CR (controller -> device). The IO-CR defines
    the cyclic frame: the FrameID, the data layout (which submodule data go at
    which offset), the send clock factor, the reduction ratio, the phase, and
    the watchdog (data-hold) factor.
  - Record-Data-CR : the ACYCLIC channel for reading/writing records
    (parameters, diagnosis, I&M identification & maintenance data) using
    Read/Write services over CL-RPC. One Record-Data-CR per AR.
  - Alarm-CR : the channel for alarms (acyclic, but real-time, using EtherType
    0x8892 alarm FrameIDs). Carries process alarms, diagnosis alarms,
    plug/pull alarms, etc., with low-priority and high-priority alarm queues
    and an acknowledge handshake.

The cyclic exchange parameters:
  - Send Clock : the base cycle time. The send clock factor multiplies the
    31.25 us base; common send clock = 32 -> 1 ms cycle (31.25 us * 32). Range
    of send-clock factor typically 1..128 (31.25 us .. 4 ms).
  - Reduction Ratio : how often (in multiples of the send clock) a given CR is
    actually transmitted; a slow signal can use a larger reduction ratio so it
    is sent every Nth send-clock, spreading load (phase / frame offset within
    the send cycle).
  - Watchdog (data-hold time) = reduction_ratio * send_clock * watchdog_factor.
    If no valid frame arrives within the watchdog, the consumer flags the data
    as invalid (IOPS BAD) and the AR may go to error.


===============================================================================
6. CYCLIC PROCESS DATA — PNIO, IOPS / IOCS, CYCLE COUNTER, DATA STATUS
===============================================================================

Cyclic ("PNIO") data is the heart of PROFINET IO real-time exchange. Each
IO-CR carries, in one Ethernet frame (EtherType 0x8892):

  - For each submodule that contributes data, an IO Data Object followed by its
    provider status IOPS, OR, for a consumer-only submodule, its consumer
    status IOCS.
  - IOPS (IO Provider Status, 1 byte per data object) : tells the consumer
    whether the producer considers this data item GOOD (valid) or BAD
    (invalid). The high bit = state (Good/Bad); lower bits carry additional
    qualifier (e.g. instance, detail).
  - IOCS (IO Consumer Status, 1 byte per data object) : the feedback in the
    reverse frame, telling the producer whether the consumer accepted the data
    (Good/Bad).
  - Every cyclic data object therefore travels with its own provider/consumer
    status, so that partial validity (a single failed channel) can be
    signalled per submodule without invalidating the whole frame.

APDU Status (appended after the cyclic data block, before the FCS):
  - Cycle Counter (2 bytes) : incremented every send-clock base (31.25 us
    ticks); lets the consumer detect missed/duplicated/late frames.
  - Data Status (1 byte) : bit-field including the State (Primary/Backup for
    system redundancy), Redundancy, DataValid (the provider's overall valid
    flag for the whole frame), Provider State (Run/Stop), Station Problem
    Indicator (a station-level diagnosis summary bit).
  - Transfer Status (1 byte) : transfer-level status (0 = ok in the normal
    case).

The consumer uses Cycle Counter + Data Status + per-object IOPS together with
the watchdog timer to decide whether the cyclic input is currently usable.

Provider / Consumer relationship:
  - For each IO-CR there is a PROVIDER (the side that produces the data) and a
    CONSUMER (the side that consumes it). For inputs the IO-Device is the
    provider and the IO-Controller is the consumer; for outputs it is reversed.
    PROFINET is a provider/consumer model, not a request/response model, for
    cyclic data.


===============================================================================
7. ACYCLIC DATA — CL-RPC / DCE-RPC, RECORDS, I&M
===============================================================================

Acyclic services (parameterization, diagnosis, identification) use the
Connectionless RPC (CL-RPC), which is the DCE/RPC (Distributed Computing
Environment Remote Procedure Call) protocol carried over UDP/IP (NRT class).

  - Connect / Release : establish / tear down the AR.
  - Write / Read (record data) : access records by API, slot, subslot, and
    Index. Standard indices include the I&M (Identification & Maintenance)
    records I&M0..I&M4 (manufacturer, order ID, serial number, hardware/software
    revision, function/location tag), parameter records, and diagnosis records.
  - Control : ParameterEnd, ApplicationReady, and similar phase-control calls
    that sequence the start-up.
  - DControl / CControl : controller-/device-side control of the start-up
    state machine (e.g. the device sends ApplicationReady when its modules are
    parameterized).

Record-Data-CR carries these Read/Write/Control records inside the AR. The
Read/Write addressing is (API, Slot, Subslot, Index, Length).


===============================================================================
8. CONFORMANCE CLASSES (CC-A / CC-B / CC-C)
===============================================================================

PROFINET defines Conformance Classes that bundle features for interoperable
device certification:

  - Conformance Class A (CC-A) : RT communication on an existing (possibly
    wireless / existing infrastructure) Ethernet. Basic cyclic RT data, acyclic
    parameter/diagnosis, alarms, DCP addressing. No topology requirements.

  - Conformance Class B (CC-B) : CC-A plus network diagnosis and topology
    information via SNMP / LLDP, supporting engineering of the network and
    device replacement without an engineering tool (neighborhood-based name
    assignment). PROFINET MRP (Media Redundancy Protocol) is added in the CC-B
    extension for ring redundancy.

  - Conformance Class C (CC-C) : CC-B plus IRT (Isochronous Real-Time) —
    hardware-supported bandwidth reservation and clock synchronization for
    high-performance, deterministic, jitter-free communication (motion
    control). CC-C devices contain a PROFINET ASIC/FPGA with the IRT scheduler
    and PTCP time sync.

A device's GSDML declares the conformance class(es) it supports. CC-C implies
the IRT-capable hardware; CC-A/CC-B can be implemented on a standard Ethernet
controller with a software/firmware real-time stack.


===============================================================================
9. TIME SYNCHRONIZATION — PTCP — AND IRT SCHEDULING
===============================================================================

PTCP (Precision Transparent Clock Protocol):
  - The PROFINET time-synchronization protocol (defined in IEC 61158, related
    to but distinct from IEEE 1588 PTP). It establishes a Sync Master and Sync
    Slaves within a SYNC DOMAIN, measures line delay (delay request/response),
    and disciplines the local clocks so all IRT devices share a common time
    base with sub-microsecond accuracy.
  - PTCP frames use EtherType 0x8892 with the PTCP FrameID range
    (0xFF00-0xFF8F: Sync, FollowUp, Delay).
  - The Sync Master is usually the IRT IO-Controller or a designated sync
    master; all CC-C devices in the sync domain are Sync Slaves.

IRT scheduling:
  - The engineering tool computes an OFFLINE schedule: the send cycle is
    divided into a RED phase (reserved time slot for the scheduled IRT frames,
    sent at exactly planned times on planned ports) and a GREEN phase (open for
    RT, NRT, and best-effort traffic). The schedule includes per-port,
    per-frame send/receive times.
  - Because the IRT frames travel at planned times through cut-through-capable
    switch ports, there is no queuing jitter: latency and jitter are
    deterministic (jitter < 1 us). This is what enables synchronized motion
    control across many axes.
  - IRT requires the topology to be fixed and known (hence LLDP topology and
    the offline planning). IRT frames carry the high-performance FrameID range
    (0x0100-0x0FFF).


===============================================================================
10. MEDIA REDUNDANCY — MRP
===============================================================================

MRP (Media Redundancy Protocol, IEC 62439-2):
  - Provides ring redundancy for the Ethernet topology. One device is the Media
    Redundancy Manager (MRM); the others are Media Redundancy Clients (MRC).
  - The MRM blocks one of its two ring ports in normal operation (so the ring
    is logically a line, no loop), and sends MRP test frames around the ring.
    On a link/port failure the MRM unblocks the secondary port; recovery time
    is typically <= 200 ms (MRP) and shorter for MRP variants.
  - MRP is part of CC-B and above. (For IRT, the redundancy and the schedule
    interact; MRPD — MRP for IRT data — extends this.)


===============================================================================
11. START-UP SEQUENCE (STATE MACHINE)
===============================================================================

The normal PROFINET IO start-up proceeds:

  1. Power-up / Reset : device boots, Ethernet link comes up
     (auto-negotiation), MAC active.
  2. Addressing (DCP) : the device has (or is assigned via DCP-Set) its
     NameOfStation and IP configuration. DCP-Hello may be sent. The
     IO-Controller resolves the configured station name to the device's MAC/IP
     (DCP-Identify by name).
  3. Connect (AR establishment) : the IO-Controller sends Connect.req
     (CL-RPC) with the expected configuration; the IO-Device validates the
     module/submodule layout and answers Connect.res. The IO-CR(s),
     Record-Data-CR, and Alarm-CR are created.
  4. Parameterization : the IO-Controller writes the parameter records to each
     submodule (Write records) and signals ParameterEnd.
  5. ApplicationReady : the IO-Device signals that its application/modules are
     ready (ApplicationReady / DControl-CControl).
  6. Cyclic data exchange (DataExchange) : both sides begin sending the cyclic
     IO-CR frames at the send clock; IOPS/IOCS valid; APDU Cycle Counter
     running; watchdog armed. The AR is now in the "in data exchange" state.
  7. Run : alarms are exchanged on events; acyclic Read/Write on demand;
     diagnosis maintained.
  8. Error / Abort : a watchdog timeout, AR abort (RPC), or fatal diagnosis
     tears down the AR; the device returns toward step 2/3 to re-establish.


===============================================================================
12. DIAGNOSIS AND ALARMS
===============================================================================

PROFINET diagnosis is channel-, submodule-, and module-oriented:
  - Channel Diagnosis : a fault on a specific channel (e.g. wire break, short,
    over-temperature) with a ChannelErrorType code, ChannelNumber, and
    severity (maintenance required / maintenance demanded / fault).
  - Alarms (sent on the Alarm-CR, EtherType 0x8892):
      Diagnosis Alarm (appearing / disappearing),
      Process Alarm,
      Plug / Pull Alarm (a module was inserted/removed in a slot),
      Return-of-Submodule Alarm,
      Status / Update Alarm.
    Alarms have a low and a high priority queue and an explicit acknowledge.
  - The Data Status bit "Station Problem Indicator" gives the controller a
    quick station-level health summary in every cyclic frame.
  - I&M (Identification & Maintenance) records provide standardized device
    identification for asset management.


===============================================================================
13. SECURITY
===============================================================================

Classic PROFINET IO has no built-in cryptographic protection of the cyclic
real-time path; security relies on network segmentation, the security classes
of the automation cell, and defense-in-depth (firewalls, zones/conduits per
IEC 62443). The integrity of cyclic frames against transmission errors is
provided by the Ethernet FCS (CRC-32) plus the APDU Cycle Counter / Data Status
and the IOPS/IOCS per-object validity. PROFINET Security (a later PI
specification layer) adds authentication and integrity for the engineering and
acyclic channels; it is layered above the classic IO data path and is out of
scope for the base cyclic protocol described here.


===============================================================================
14. VERSIONING
===============================================================================

PROFINET is standardized in IEC 61158 (Type 10 — PROFINET IO services, protocol
and application layer) and IEC 61784-2 (CPF 3, the communication profiles
RT_CLASS_1 / RT_CLASS_2 / RT_CLASS_3(IRT) / RT_CLASS_UDP). It is maintained by
PI (PROFIBUS & PROFINET International). The performance classes (NRT, RT, IRT),
the conformance classes (CC-A, CC-B, CC-C), the GSDML device-description schema,
the DCP addressing protocol, the AR/CR connection model, the cyclic PNIO data
with IOPS/IOCS and APDU status, the acyclic CL-RPC records, the PTCP time
synchronization, and the MRP media redundancy together define the PROFINET IO
communication standard.

PROFINET deliberately distinguishes itself from its serial predecessor PROFIBUS
(RS-485 token-passing fieldbus with SD1-SD4 telegram frames, the keyword-based
GSD file, and DPV1 acyclic services): PROFINET is full Ethernet, uses the XML
GSDML (not the GSD text format), names instead of bus addresses, and the
provider/consumer cyclic model with IO-Controller / IO-Device / IO-Supervisor
roles instead of DP master / DP slave.
