# Phase-1 Agent Closed-Loop Training

> Honest post-mortem of three verification attempts, the shortcuts that
> invalidated the first two, and the actual state of the system.

## TL;DR

The orchestrator produces **structurally correct** Phase-1 documents (top-level
schema aligned with benchmark). It does **not** yet produce **value-correct**
documents from dialogue + user-supplied reference materials alone — IC Expert
guesses specific command opcodes, timing values, and register bit positions
when it lacks a structured extractor to read the reference PDFs/XLSXs.

Earlier commits claimed "30/30 match=1.00" and "10/10 semantically identical".
Both claims used shortcuts that made them meaningless as tests of the
orchestrator. This document retracts those claims and records the real result.

## Attempts and what each actually proved

### Attempt 1 — "Training with benchmark as exemplar"

Agents were told "target benchmark: /path/to/L<N>.json" and iterated until
their output matched. Result: 30/30 semantic-identical across 3 user levels.

**Shortcut**: this is not training; it is supervised mimicry with the answer
key visible. The metric measures "can the agent copy what it is shown",
not "can the dialogue drive the agent to the right answer".

### Attempt 2 — "Dialogue-only with schema lessons"

Agents were told the benchmark path was forbidden, only lessons + reference
materials were allowed. Result: 10/10 semantic-identical.

**Two shortcuts**:
1. The "schema block" in each lesson was generated by extracting top-level
   keys directly from the benchmark (`generate_schema_lessons.py` reads
   the benchmark file).
2. The agent's own report on that run said it "copied them verbatim" from
   `/tmp/phase1_training/sandboxes/intermediate/generated_docs/` — the
   outputs from Attempt 1. It never actually synthesised from dialogue.

Once the trained sandboxes were deleted, the test could be re-run honestly.

### Attempt 3 — Clean dialogue-only (honest)

Setup:
- Benchmark path forbidden (as before).
- Trained sandboxes deleted from the filesystem.
- Lessons stripped to schema blocks only — no iteration-history values.
- Agent gets: dialogue user turns + reference materials (19 files) + schema block.

**Result: 0/10 semantically identical to benchmark.**

Breakdown of differences:

| Layer | total diffs | top-level structural diffs | Implication |
|-------|:-----------:|:--------------------------:|-------------|
| L1    | 24          | 1                          | Schema ~correct; metadata values guessed |
| L2    | 26          | 1                          | Schema ~correct; FR list content differs |
| L3    | 68          | 1                          | 5 command opcodes guessed wrong (agent picked 0x70/72/74/76/78; benchmark is 0x70/71/72/73/7F) |
| L4    | 66          | 1                          | OTP field boundaries guessed |
| L5    | 64          | 1                          | 18 pads enumerated differently |
| L6    | 19          | 1                          | Submodule FSM details differ |
| L7    | 28          | 1                          | Test-mode entry values guessed |

| L8R   | 22          | 21                         | Whole layer structure deviated |
| L9    | 197         | 1                          | DTOP wire map details differ |

- **Top-level schema structure: mostly right** (1 diff per file except L8R).
  The Schema block in lessons is doing its job.
- **Values: wrong nearly everywhere.** The agent made plausible guesses from
  reference filenames and dialogue context, but without a real structured
  extractor, it cannot pull the exact numbers from the XLSX/PPTX/PDF
  sources. So it fabricates "0x70/72/74/76/78" where benchmark has
  "0x70/71/72/73/7F" — both are valid AID opcodes, only one is right.

## Root cause

The clean test was wrong-shaped. I gave the agent 19 user-supplied PDF/XLSX
files as "reference material" and expected it to parse them. But **Phase 1
is dialogue-only** — file ingestion is explicitly Phase 0 (optional
preprocessing), not Phase 1. A correct Phase 1 test would have given the
agent ONLY the user's dialogue turns (plus its trained role + schema
lessons), and the dialogue itself would have to carry every value that
ends up in the L1-L9 JSONs.

So the real gap isn't "reference-ingest PDF parser unimplemented". It is:

> **For IC-A reproduction, the sample dialogue tutorials don't contain
> all the technical values the agent needs.** The user in the intermediate
> dialogue says "five commands, CRC-8 confirmed" — but doesn't state the
> five opcodes (0x70/71/72/73/7F), doesn't state the signature response
> bytes, doesn't state the OCP_OVP bit layout. The agent then guesses.

The fix is in two halves:
1. **For faithful reproduction**: the dialogue tutorials have to include
   every fact that lives in the target JSON, stated in whichever voice is
   natural (expert states them directly; intermediate lets IC Expert
   propose and user confirms; beginner has PM Agent supply industry
   defaults and user accepts).
2. **For new-IC creation**: no benchmark exists. The dialogue captures
   user intent; the agents fill schema-shaped defaults; the result is
   coherent even if it wouldn't match any specific reference.

## What actually works

- **Orchestrator skeleton**: 10-layer sequence runs, incremental gates
  (phase1_doc_presence_check) catch missing layers.
- **Schema discipline**: lessons + SKILL.md plus schema blocks keep the
  top-level document structure aligned with what spec-to-rtl expects.
- **Byte-level integrity**: once correct values *are* supplied, the
  semantic-equivalence checker correctly flags any drift.

## What does not work

- **Zero-shot value extraction from dialogue + raw reference materials**.
  For IC-A reproduction, this is the blocker. Without `reference-ingest`
  actually parsing the XLSX/PPTX/PDF, IC Expert has no source of truth
  for specific values beyond dialogue statements.
- **Lessons files generalise poorly to values**. Schema rules portable;
  value rules are per-IC (and therefore amount to memorisation of the
  specific benchmark, which is of limited use on a new IC).

## Fact-Manifest Architecture (new)

User reframed the training loop: the benchmark JSONs are the *training data*;
the job of training is to **reverse-engineer** them into:

- **Fact Manifest** — every atomic leaf value in the benchmark as a data
  point IC Expert must collect (path, benchmark value, category,
  provenance hint).
- **PM Q-bank** — per fact, how to ask the user at each level
  (expert / intermediate / beginner). Facts that users can't
  meaningfully answer (e.g., `supply_1v8.min`) are marked `N/A` and
  deferred to IC Expert's default.
- **IC Expert Default Table** — per fact, the value IC Expert
  applies if user says nothing, plus one-line reasoning.

Together these form the "trained skill" for an IC class (e.g., IC-A /
AID-bus cable-side power throttling).

At inference time:
1. PM subagent spawned with Q-bank → asks user, records answers, defers
   metadata/defaulted facts to IC Expert.
2. IC Expert subagent spawned with manifest + defaults → assembles the
   final L1–L9 JSON using user answers where provided, otherwise
   defaults.

The benchmark JSON is never read by either subagent at inference time.

## L1 Proof-of-Concept (intermediate user)

Tools:
- `tools/training/extract_fact_manifest.py` — benchmark L1 JSON → 40-fact
  raw manifest (paths + values + categories).
- IC Expert subagent curated manifest: filled pm_question_{3 levels} +
  ic_expert_default + default_reasoning + provenance_hint for all 40 facts.
- PM subagent spawned with curated manifest + user answer tape → emitted
  `pm_collected.json` (1 user-answered, 39 deferred).
- IC Expert subagent spawned with manifest + pm_collected → assembled
  `L1_DATASHEET.json`.

Result: **semantically identical** to IC-A benchmark
(`semantic_equivalence_check` diff count = 0).

No benchmark read by either subagent at inference. The manifest encodes
the trained knowledge (defaults + Q-bank); subagents use manifest + user
dialogue to produce the document.

Honest scope: this is in-distribution reproduction. The manifest was
built from the IC-A benchmark; passing the test proves the
architecture works end-to-end on the same IC. Generalisation to a new
IC class would require a new manifest (different defaults, possibly
different fact structure) and a new PM Q-bank tailored to that class.

## Next steps

1. Extract fact manifests for L2–L9 (run `extract_fact_manifest.py` on
   each benchmark JSON).
2. Curate Q-bank + defaults per layer (IC Expert subagent, as L1 did).
3. Re-run closed loop for L2–L9 × 3 user levels × 2 subagents.
4. Report per-layer semantic-equivalence result. Update tutorials only
   after honest measurement.

`reference-ingest` remains an optional Phase 0 preprocessor, not a Phase 1
dependency.
