# Program re-entry from a preserved, signed pre-gate input

`benchmark_dispatch.py --resume --program-regate REQUEST.json` re-runs a FIXED
Program over the exact signed input a previous, buggy Program consumed. It is
shared by every adapter using the normal dispatcher. It does not author RTL,
choose a route, invoke a scorer, accept a candidate, or grant a repair permit.

It is the sibling of `--review-correction`, not a mode of it. That operation
keeps the frozen RTL unchanged and advances a review; this one keeps the
AUTHOR unchanged and regenerates the Program's output. The two are refused
together: one operation per resume.

## The state this exists for

A deterministic gate can normalize a signed author candidate into different
bytes before freezing it. The author signed `H_in`; the frozen candidate is
`H_stale`. The installed refusal

    AI repair record repaired_rtl_sha256 is stale or wrong

is then CORRECT, and it is not weakened here.

Once that transform is fixed, the pending task is stuck three ways at once:

* its unchanged working output is not re-gated, because nothing changed;
* restoring the signed input reads as a NEW AI edit, so the repair predicate
  demands a semantic counterexample against the unwanted transformed
  candidate — a test the author has no reason to be able to write;
* re-signing the unwanted output would attribute a PROGRAM mutation to the AI
  author, which is simply false.

The missing behaviour is none of those three. It is an explicit,
evidence-bound Program RETRY.

## Preservation is what makes the retry possible

The gates normalize the work tree IN PLACE, so the only copy of what the
author signed is destroyed at the moment it stops being reproducible. At the
ordinary runner boundary the signed bytes are therefore frozen first, under
`pre_gate_inputs/<safe-id>/<signed sha>/`, with a manifest naming the Program
version that is about to consume them. When the gates return, the produced
hash is bound to that input in `gate_output_<output sha>.json`.

The pair (signed input sha, gate output sha) is thus a RECORDED FACT with the
Program version attached, not something reconstructed after a bug is found.
Both files are immutable: identical bytes are a no-op, different bytes raise.

## Request and invocation

```json
{
  "schema": "vibeic.benchmark.program_regate.v1",
  "id": "<current task id>",
  "task_sha256": "<canonical task digest>",
  "prompt_sha256": "<task.prompt_sha256>",
  "signed_input_sha256": "<the hash the AI author actually signed>",
  "stale_output_sha256": "<task.rtl_sha256, the unwanted frozen output>",
  "program_version_before": "<the Program that produced the preserved input>",
  "program_version_after": "<the running, fixed Program>",
  "author": {"kind": "AI", "model": "<actual requesting model>"},
  "blind": {"oracle_accessed": false},
  "rationale": "<at least 80 characters naming the fixed transform>"
}
```

The canonical task digest is SHA256 of UTF-8
`json.dumps(task, ensure_ascii=False, sort_keys=True)`, without a trailing
newline, exactly as `--review-correction` defines it.

```bash
python3 programs/benchmark_dispatch.py <bench> --resume \
  --dataset <dataset> --run <run> --jobs 1 --heavy-jobs 1 --worker-threads 1 \
  --program-regate <request.json>
```

`--program-regate` is invalid with solve, score, show or list, and invalid
together with `--review-correction`. Expected outcome is pending (exit 2), not
a successful score.

## Attribution: what is bound to whom

The author's repair record is never rewritten. Its `repaired_rtl_sha256`
remains the hash of the bytes the author actually wrote.

`_signed_candidate_hash(task)` is the single place that decides which hash an
author's signature must cover. With no re-entry record it returns
`task["rtl_sha256"]` — byte-identical to the behaviour before this change.
It returns the preserved signed input ONLY when `_verified_program_regate`
proves every one of:

* the record carries this schema;
* `new_output_sha256` is this task's own frozen candidate;
* `program_version_before` and `program_version_after` are both present and
  different, AND `program_version_before` is the version recorded on the
  preserved input manifest — so the pair is cross-checked against an artefact,
  not merely asserted by the request;
* the preserved input manifest is readable, names this task, and the bytes
  still on disk hash to `signed_input_sha256`.

A record failing ANY of these is treated as absent, and the ordinary refusal
applies unchanged. "Could not read it" is never "read it and it matched": an
unreadable preserved input binds nothing.

The regenerated bytes are recorded as `attributed_to: "PROGRAM"` with
`author_signature_unchanged: true` and `repair_authorized: false`.

## State, refusal and restart contract

This is **BLOCKING**: invalid requests stop before ordinary resume and emit
`PROGRAM_REGATE_REFUSED`. A second coordinator is refused by the existing
run-root lock — which delays the operation, it does not permanently refuse it.
Rejected conditions include a wrong or stale request schema/id/task digest/
prompt/stale-output hash; an unattributed or non-blind request; a rationale
under 80 characters; a candidate that is not an `AI_REPAIR`; a
`signed_input_sha256` that is not the hash the author signed; gates that did
not in fact change the signed input; an unchanged Program version (a retry
with the same Program is a loop, not a fix); a `program_version_after` that is
not the running Program; a `program_version_before` that is not the Program
that produced the preserved input; a missing, unbound or drifted preserved
input; a working tree that drifted from the frozen gate output; prompt or
inherited-challenge drift; symlinked or out-of-run evidence; and an already
accepted or published candidate.

Immutable records live under
`program_regates/<safe-id>/<request-file-sha256>/`: the prior task, the prior
gate output's manifest, the exact request, and a transition containing both
task states and source hashes. Archive creation finishes before one atomic
replacement of the authoritative review worklist, and only then is the
preserved input restored into the work tree.

- Before the commit, interruption leaves the old task active. Repeat the
  identical request to reuse identical prepared archives and finish.
- After the commit but before the gates run, the task carries
  `status: REGATE_PENDING`. Ordinary resume re-enters the runner from the
  restored input; the final-provenance refusal stands aside for exactly this
  one state, because the stale embedded provenance is the condition the
  re-entry exists to resolve.
- After the gates consume it, the status is `FRESH_REVIEW_REQUIRED` and the
  same request reports `ALREADY_APPLIED` against its verified archive. It
  never opens a second round.

## What it must not do

It does not attribute the regenerated bytes to the AI author, supersede or
retire any challenge, accept or publish anything, or skip the normal gates.
The regenerated output goes through the SAME downstream obligations as a
first-time output: fresh review and challenge paths are issued unoccupied, the
inherited challenge list is carried forward unchanged, and the acceptance
report shows the task PENDING with no accepted ids.

## Verification boundary

`programs/tests/test_program_regate.py` drives the real coordinator: it builds
the stuck state through `cmd_resume` with a gate that normalizes the work tree,
pins that the installed stale-signature refusal still fires with no re-entry
record, then exercises the happy path in two shapes — a fixed Program that
preserves the signed bytes exactly, and one that still normalizes benignly into
a third distinct hash, which is the case where `_signed_candidate_hash` is
load-bearing. Each refusal has a test, and the binding tests break exactly one
field at a time and confirm the frozen candidate governs again.

The pre-fix control runs the same real resume entry when the operation does not
exist, via a `cmd_resume` signature probe; it is graded on the state left
behind, not on a missing attribute. Two tests are green on BOTH trees by
design — they assert the installed refusal still refuses — and that is what
makes them guards rather than feature tests.

These are focused flow tests, not an official benchmark score or a claim of
full-flow compliance.
