THE REFUSE COLUMN IS THE ONE USUALLY MISSING. A checker that returns 0 when it
cannot see its subject is the empty-denominator defect this whole branch is
about, so each verifier here exits 2 and says NOT VERIFIED instead. That is the
repo's own rule (gate_zero_denominator_refuses_check, #564) and the same shape
the flow owner required of PAD_ROTATION_VERTICAL: refuse, never pass quietly.

WHAT IS *NOT* CLAIMED: that these verifiers are complete. They are graded, which
is a different and weaker property. Coverage of the CODE is the 15-behaviour
sweep with its own stated denominator; coverage of the REPORT is bounded by the
figures the self-check knows to read.

GRADING THE REFUSAL PATH FOUND A DEFECT IN THE GRADER ITSELF
============================================================
The sky130A checks read two evidence JSONs. When one was missing, the file
printed "[NOT VERIFIED] ... a refusal, not a pass" -- and then EXITED 1, the same
code as a real disagreement. It said refusal and scored failure.

THAT IS THE #492 CONFLATION, IN MY OWN TOOL, ONE DAY AFTER I SENT THE PUBLISHING
AGENT #492 AS A FINDING. flow_compliance_check.py:7220 records it: rc 2 carried
"there was no input to check" and "you called me wrongly" at once, and treating
them alike "is what let 39 registered gates be permanently silent while the
umbrella advertised that all of them ran". I reproduced it by hand while writing
a checker whose subject is that exact defect.

Separated, and all three states now measured:

    rc=0  ALL CHECKS PASS                       the report re-derives
    rc=1  10 FAILED                             die 2.262 -> 2.300 in RESULT.md
    rc=2  NOT VERIFIED: 1 could not see its     an evidence JSON removed
          subject -- not a pass and not a
          failure

IT WAS ONLY VISIBLE BECAUSE THE REFUSAL PATH WAS GRADED. Running the file green,
and even running its FAIL path, would never have shown it: both were correct. The
bug lived entirely in the third state, which is the one nobody exercises.

A VACUITY AUDIT OF THE SELF-CHECK ITSELF, BY PERTURBING ITS SUBJECT
===================================================================
The file had grown to 50 checks by accretion, so: perturb the report (die,
split, the five dies, both minima) and see which checks STILL PASS. 35 did.

MOST OF THOSE 35 ARE CORRECT. They bind ARTEFACTS -- the sky130A JSONs, the
pre/post ring comparison, the two DEFs -- and a report perturbation should not
move them. Reading the number alone as "35 vacuous checks" would have been the
same denominator error this file is about.

THREE WERE GENUINELY TAUTOLOGICAL, comparing constants defined at the top of the
file to each other, unable to fail whatever the PDK or the artefacts said:

    PAD != DEPTH          75 != 350, always
    CORNER != DEPTH       355 != 350, always
    RING == 376           26 + 350, always

That is the tautology already removed from the ratio section once, reintroduced
three times while adding the section that WARNS about confusing the two
dimensions. Fixed by DERIVING the constants from the artefact instead of
asserting them: the pad master's width and height and the corner's width are now
read out of the placed ring, plus a check that the vertical pads are the same
cell rotated. GRADED: setting the placed pad width to 99000 in the artefact
turns it red.

    [FAIL] PAD is the pad master's width, as placed: {99000} (expected {75000})

54 checks now, and the ring depth is read out of the report's own table rather
than recomputed from the constants -- so the report and the artefact have to
agree with each other, not merely each with me.
