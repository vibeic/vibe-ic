IEEE 1588 Precision Time Protocol (PTP) — Hardware Implementation Specification
================================================================================

Document title: IEEE 1588 Precision Time Protocol (PTP) Clock Synchronization
                Engine — Specification for a Hardware-Timestamping PTP Node
Standard:       IEEE Std 1588-2008 (PTPv2) and IEEE Std 1588-2019; IEEE 802.1AS
                (gPTP) profile for Audio/Video Bridging and Time-Sensitive
                Networking (TSN)
Editor:         IEEE 1588 Working Group (Precision Networked Clock
                Synchronization)
Copyright:      © IEEE — Precision Time Protocol


1. Scope and Overview
---------------------

The Precision Time Protocol (PTP), standardized as IEEE 1588, provides
sub-microsecond clock synchronization of distributed real-time clocks over a
packet-switched network. PTP synchronizes the local clocks of networked nodes
to a single reference clock — the Grandmaster — by exchanging timestamped
event messages and computing the offset from master and the mean path delay
between each node and its master.

This specification describes a hardware PTP node (a PTP clock) that implements
the PTPv2 (IEEE 1588-2008/2019) protocol with hardware timestamping at the
MAC/PHY boundary. The node participates in a master-slave clock hierarchy that
is established and maintained by the Best Master Clock Algorithm (BMCA). The
root of the synchronization hierarchy is the Grandmaster clock; all other
clocks discipline their local time to the Grandmaster.

PTP is a master-slave protocol: in each PTP communication path one port acts in
the MASTER state (the time source) and the other port acts in the SLAVE state
(the time receiver). The BMCA continuously elects, per port and per domain, the
best available clock and assigns each port the MASTER, SLAVE, or PASSIVE state.

PTP achieves precision well below one microsecond (typically tens of
nanoseconds with hardware timestamping) because event messages are timestamped
as close to the physical layer as possible — ideally at the MAC/PHY reference
plane — removing the variable software and queueing latency that would
otherwise dominate the error budget.


2. Clock Types
--------------

PTP defines the following PTP clock types:

  - Ordinary Clock (OC): a clock with a single PTP port. An Ordinary Clock is
    either a Grandmaster (the time source) or a slave-only node that
    synchronizes to its master. Most end devices are Ordinary Clocks.

  - Boundary Clock (BC): a clock with multiple PTP ports. One port is in the
    SLAVE state and synchronizes to an upstream master; the remaining ports are
    in the MASTER state and serve downstream slaves. A Boundary Clock
    terminates and regenerates PTP, isolating timing domains and removing
    accumulated packet delay variation.

  - Transparent Clock (TC): a switch/bridge that measures the residence time of
    each PTP event message as it transits the device and adds that residence
    time to the message correctionField, so downstream clocks can subtract the
    switching delay. Two variants are defined:
        * End-to-End Transparent Clock (E2E TC): corrects residence time and
          forwards the delay-request-response messages transparently.
        * Peer-to-Peer Transparent Clock (P2P TC): corrects residence time AND
          measures the link delay to each neighbor using the peer delay
          mechanism (Pdelay_Req / Pdelay_Resp / Pdelay_Resp_Follow_Up).

  - Management Node: a node that issues management messages to configure and
    monitor PTP clocks.

The Grandmaster is the OC or BC port elected by the BMCA as the root of the
master-slave hierarchy for a domain; it provides the time reference for all
other clocks in that domain.


3. PTP Message Classes and Message Types
----------------------------------------

PTP messages are divided into two classes:

  - Event messages: timestamped on transmission and reception. The accuracy of
    PTP depends on the precision of these timestamps. Event messages are:
        Sync, Delay_Req, Pdelay_Req, Pdelay_Resp.

  - General messages: not timestamped; they carry data. General messages are:
    Follow_Up, Delay_Resp, Pdelay_Resp_Follow_Up, Announce, Signaling,
    Management.

Message types (messageType field, 4 bits):

  Sync                   (0x0) — event   — master broadcasts the synchronization
                                            message carrying or referencing the
                                            transmit timestamp T1.
  Delay_Req              (0x1) — event   — slave sends a delay request; its
                                            transmit time is T3.
  Pdelay_Req             (0x2) — event   — peer delay request (P2P mechanism).
  Pdelay_Resp            (0x3) — event   — peer delay response (P2P mechanism).
  Follow_Up              (0x8) — general — in two-step operation, carries the
                                            precise transmit timestamp T1 of the
                                            preceding Sync.
  Delay_Resp             (0x9) — general — master returns T4, the receive time
                                            of the slave's Delay_Req.
  Pdelay_Resp_Follow_Up  (0xA) — general — carries the precise turnaround
                                            timestamps for the P2P mechanism.
  Announce               (0xB) — general — carries the clock quality attributes
                                            (clockClass, clockAccuracy,
                                            offsetScaledLogVariance, priority1,
                                            priority2, grandmasterIdentity) used
                                            by the BMCA.
  Signaling              (0xC) — general — negotiation of unicast and other
                                            options.
  Management             (0xD) — general — read/write of clock data sets.

PTP common header fields include: messageType, versionPTP, messageLength,
domainNumber, flags, correctionField (a 64-bit signed scaled-nanoseconds
field), sourcePortIdentity, sequenceId, controlField, and
logMessageInterval.


4. Synchronization Mechanisms and Timestamps T1..T4
---------------------------------------------------

4.1 Delay-Request-Response Mechanism (end-to-end)

The end-to-end delay mechanism measures the offset of a slave clock from its
master and the mean path delay using four timestamps:

  T1 — time at which the master transmits the Sync message.
  T2 — time at which the slave receives the Sync message.
  T3 — time at which the slave transmits the Delay_Req message.
  T4 — time at which the master receives the Delay_Req message.

Sequence:
  1. The master sends a Sync message and captures its egress timestamp T1.
        - One-step clock: T1 is written into the Sync message originTimestamp
          on the fly.
        - Two-step clock: the Sync carries an estimate; the precise T1 is sent
          afterwards in a Follow_Up message.
  2. The slave timestamps the arrival of Sync as T2.
  3. The slave sends a Delay_Req and captures its egress timestamp T3.
  4. The master timestamps the arrival of Delay_Req as T4 and returns it to the
     slave in a Delay_Resp message.

Assuming a symmetric link, the slave computes:

     meanPathDelay = [ (T2 - T1) + (T4 - T3) ] / 2
     offsetFromMaster = (T2 - T1) - meanPathDelay
                      = [ (T2 - T1) - (T4 - T3) ] / 2

The slave then corrects its local clock (the servo / PI controller adjusts the
local oscillator frequency and phase) to drive offsetFromMaster toward zero.
The correctionField accumulated by Transparent Clocks along the path is
subtracted so that residence and link delays do not bias the result.

4.2 Peer Delay Mechanism (peer-to-peer)

The peer-to-peer mechanism measures the link delay between directly connected
ports independently of the master-slave path. Each port periodically:
  1. Sends Pdelay_Req and captures t1.
  2. The peer captures the receive time t2, sends Pdelay_Resp capturing t3, and
     reports t2 and t3 (in Pdelay_Resp and Pdelay_Resp_Follow_Up).
  3. The requestor captures the Pdelay_Resp receive time t4.
The link delay is meanLinkDelay = [ (t4 - t1) - (t3 - t2) ] / 2. This is the
mechanism used by IEEE 802.1AS (gPTP) and by Peer-to-Peer Transparent Clocks.


5. Best Master Clock Algorithm (BMCA)
-------------------------------------

The Best Master Clock Algorithm selects, for each PTP domain, the clock that
becomes the Grandmaster, and assigns each port a recommended state (MASTER,
SLAVE, or PASSIVE). The BMCA is fully distributed: each clock runs the same
algorithm using the Announce messages it receives.

The dataset comparison algorithm compares clocks by, in order:
  1. priority1 (user-configurable preference, lower is better),
  2. clockClass (traceability of the time source),
  3. clockAccuracy,
  4. offsetScaledLogVariance (clock stability),
  5. priority2 (user-configurable tie-break),
  6. clockIdentity (final tie-break — guarantees a deterministic winner).

The clock with the best dataset becomes the Grandmaster. Each port then enters
the MASTER, SLAVE, PASSIVE, LISTENING, PRE_MASTER, UNCALIBRATED, FAULTY, or
DISABLED state per the PTP state machine. Announce messages advertise the
attributes (clockClass, clockAccuracy, grandmasterIdentity, stepsRemoved) that
drive the comparison. The grandmasterIdentity propagates so every node knows
the root of the hierarchy.


6. Transport
------------

PTP messages are carried over one of several network/transport layers
(annex-defined mappings):

  - IEEE 802.3 / Ethernet (Layer 2): PTP frames use EtherType 0x88F7. Event and
    general messages may use distinct multicast MAC addresses
    (01-1B-19-00-00-00 for non-peer-delay, 01-80-C2-00-00-0E for the
    peer-delay messages). This is the transport used by IEEE 802.1AS (gPTP).
  - UDP/IPv4 and UDP/IPv6: PTP event messages use UDP destination port 319 and
    general messages use UDP destination port 320, sent to defined multicast
    addresses (224.0.1.129 etc.).

PTP organizes nodes into domains (domainNumber); clocks in different domains
maintain independent synchronization hierarchies and do not interact.

Note: although PTP is transported over Ethernet, PTP is NOT an Ethernet MAC/PHY
itself. The Ethernet/UDP layer is only the carrier; the PTP timing structure
(Sync/Follow_Up/Delay_Req/Delay_Resp/Pdelay messages, BMCA, Grandmaster,
Ordinary/Boundary/Transparent Clocks, T1..T4 timestamps, offsetFromMaster +
meanPathDelay, and the correctionField/residence-time correction) is the
substance of this device.


7. PTP Profiles
---------------

A PTP profile constrains the protocol options for a specific application:

  - Default profiles (Annex J of IEEE 1588): delay-request-response (E2E) and
    peer-to-peer (P2P) default profiles.
  - IEEE 802.1AS (gPTP): the generalized PTP profile for AVB/TSN. Uses the peer
    delay mechanism on every link, two-step Sync+Follow_Up, BMCA variant
    (alternate BMCA), and Layer-2 0x88F7 transport. Every bridge is a
    time-aware system (effectively a P2P Transparent/Boundary Clock).
  - Power profile (IEEE C37.238) for electric power systems.
  - Telecom profiles (ITU-T G.8275.1 / G.8275.2) for mobile backhaul frequency
    and phase/time synchronization.


8. Hardware Timestamping
------------------------

To achieve sub-microsecond accuracy the PTP node timestamps event messages
(Sync, Delay_Req, Pdelay_Req, Pdelay_Resp) in hardware at the MAC/PHY
reference plane. A free-running hardware PTP clock counter (seconds +
nanoseconds, typically a 48-bit seconds + 32-bit nanoseconds representation,
or an 80-bit timestamp) is sampled on the detection of the Start-of-Frame /
message-start of an event message. The captured ingress/egress timestamps T1,
T2, T3, T4 (and the peer-delay t1..t4) are presented to the protocol engine /
servo. The servo (a PI controller / clock-disciplining loop) adjusts the local
clock rate (frequency) and offset (phase) to track the master.

The hardware timestamp unit must be placed so that the variable latency of the
MAC FIFO, queueing, and software stack is excluded from the T1..T4 captures;
this is why timestamping at the PHY (or at the MAC/PHY interface) is preferred
over software timestamping.


9. Functional Requirements
--------------------------

FR-SYNC-01: The node shall implement the Sync / Follow_Up exchange and the
            Delay_Req / Delay_Resp exchange (the delay-request-response
            mechanism), capturing the event timestamps T1, T2, T3, T4.
FR-PDELAY-02: The node shall implement the peer delay mechanism
            (Pdelay_Req / Pdelay_Resp / Pdelay_Resp_Follow_Up) for use by the
            peer-to-peer profile and IEEE 802.1AS.
FR-OFFSET-03: The node shall compute offsetFromMaster and meanPathDelay from
            the captured timestamps and subtract the accumulated
            correctionField.
FR-SERVO-04: The node shall discipline its local clock (frequency and phase)
            via a servo / PI controller to drive offsetFromMaster toward zero.
FR-BMCA-05: The node shall run the Best Master Clock Algorithm using received
            Announce messages to determine the Grandmaster and the MASTER /
            SLAVE / PASSIVE state of each port.
FR-CLKTYPE-06: The node shall be configurable as an Ordinary Clock, a Boundary
            Clock, or a Transparent Clock (end-to-end or peer-to-peer).
FR-TC-07: When configured as a Transparent Clock the node shall measure the
            residence time of each event message and add it to the
            correctionField.
FR-TS-08: The node shall timestamp event messages in hardware at the MAC/PHY
            reference plane (hardware timestamping) for sub-microsecond
            accuracy.
FR-XPORT-09: The node shall support PTP over Ethernet (EtherType 0x88F7) and/or
            UDP/IPv4/IPv6 (event port 319, general port 320).
FR-DOMAIN-10: The node shall support PTP domains (domainNumber); clocks in
            distinct domains shall not interact.
FR-PROFILE-11: The node shall support the default delay-request-response and
            peer-to-peer profiles and the IEEE 802.1AS (gPTP) profile.
FR-MSG-12: The node shall encode/decode the PTP common header and all PTP
            message types (Sync, Delay_Req, Pdelay_Req, Pdelay_Resp,
            Follow_Up, Delay_Resp, Pdelay_Resp_Follow_Up, Announce, Signaling,
            Management).


10. Error and Fault Conditions
------------------------------

  - Loss of Announce (announceReceiptTimeout): the slave no longer hears its
    master; the BMCA re-runs and may re-elect a Grandmaster.
  - Loss of Sync (syncReceiptTimeout): synchronization is lost; the port enters
    UNCALIBRATED / LISTENING.
  - Asymmetry error: an asymmetric link delay biases offsetFromMaster (corrected
    by a configured asymmetry correction or the peer delay mechanism).
  - Domain mismatch: a message with a foreign domainNumber is ignored.
  - Excessive offset / holdover: if the master is lost the servo holds over on
    the local oscillator.


11. State Machine
-----------------

The PTP port state machine states are: INITIALIZING, LISTENING, PRE_MASTER,
MASTER, PASSIVE, UNCALIBRATED, SLAVE, FAULTY, DISABLED. Transitions are driven
by the BMCA decision (recommended state), timeouts (announceReceiptTimeout,
syncReceiptTimeout), and management/fault events.

  INITIALIZING  -> LISTENING       (initialization complete)
  LISTENING     -> MASTER          (BMCA: this port is best master)
  LISTENING     -> SLAVE/UNCALIB.  (BMCA: an upstream master is better)
  UNCALIBRATED  -> SLAVE           (synchronization achieved)
  SLAVE         -> LISTENING       (announceReceiptTimeout: master lost)
  any           -> FAULTY          (fault detected)
  any           -> INITIALIZING    (reset)

On power-up / reset the port enters INITIALIZING, then LISTENING, where it
collects Announce messages for the BMCA before being assigned MASTER or SLAVE.


12. Verification and Compliance
-------------------------------

A compliant PTP node must:
  - Exchange Sync/Follow_Up and Delay_Req/Delay_Resp (or Pdelay) messages.
  - Compute offsetFromMaster and meanPathDelay correctly under symmetric and
    Transparent-Clock-corrected paths.
  - Run the BMCA and converge on the correct Grandmaster deterministically.
  - Provide hardware timestamps with the specified resolution at the MAC/PHY
    plane.
  - Maintain synchronization within the profile's accuracy budget
    (sub-microsecond for the default/802.1AS profiles).
  - Correctly accumulate residence time into the correctionField when acting as
    a Transparent Clock.

Conformance is established against IEEE 1588-2008 / IEEE 1588-2019 and, for the
gPTP profile, IEEE 802.1AS test suites.
