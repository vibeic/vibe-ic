Avalon Interface Specifications
Intel / Altera
Document MNL-AVABUSREF

================================================================================
1. OVERVIEW
================================================================================

The Avalon Interface Specifications describe a family of standard interfaces
used to connect components inside an FPGA System-on-a-Chip (SoC). Avalon
interfaces are the interconnect contract used by Intel (formerly Altera)
Platform Designer (formerly Qsys), the Nios II embedded processor, and the
Quartus Prime design software when composing IP cores into a system. A
component (IP core) advertises one or more Avalon interfaces; Platform Designer
generates the interconnect fabric (address decoding, arbitration, data-path
multiplexing, burst adaptation, width adaptation, clock crossing) that wires
the interfaces together.

There are seven defined Avalon interface types:

  - Avalon Memory-Mapped Interface (Avalon-MM): an address-based read/write
    interface for master/slave (host/agent) connections such as a processor
    reading and writing registers, memory, or peripherals.
  - Avalon Streaming Interface (Avalon-ST): a unidirectional point-to-point
    interface for high-throughput streaming data between a source and a sink,
    with ready/valid backpressure and optional packet framing.
  - Avalon Conduit Interface: a collection of arbitrary application-specific
    signals exported out of the system (for example, signals that go to a chip
    pin or to logic outside Platform Designer).
  - Avalon Interrupt Interface: lets a slave (interrupt sender) signal events
    to an interrupt receiver, typically the processor.
  - Avalon Clock Interface: drives or receives a clock.
  - Avalon Reset Interface: drives or receives a reset.
  - Avalon Memory-Mapped Tristate Conduit Interface (Avalon-TC): a
    memory-mapped interface that supports tristate bidirectional signals for
    connecting to off-chip devices such as flash and SRAM that share data and
    address pins.

The two primary interfaces are Avalon-MM and Avalon-ST. The other interface
types (Conduit, Interrupt, Clock, Reset, and Tristate Conduit) are supporting
interfaces. The terms "host" and "agent" are the modern equivalents of the
older "master" and "slave" terminology used throughout this family.

This document describes signal roles, transfer properties, and the timing of
each interface so that any compliant component can be connected through
Platform-Designer-generated interconnect.

================================================================================
2. AVALON MEMORY-MAPPED INTERFACE (Avalon-MM)
================================================================================

2.1 Roles
---------

An Avalon-MM interface is either a host (master) or an agent (slave). A host
initiates read and write transfers by driving an address; an agent responds. A
single component may contain several Avalon-MM interfaces, and an interface may
be a host on one port and an agent on another. Platform Designer interconnect
allows any host to access any agent it is connected to; arbitration is
generated automatically when multiple hosts share an agent.

2.2 Signal Roles
----------------

The Avalon-MM signal set is a superset; a given interface uses only the signals
it needs. Signal roles (with typical width) are:

  address       host->agent   Byte or word address selecting an agent location.
  read          host->agent   Asserted to request a read transfer.
  write         host->agent   Asserted to request a write transfer.
  writedata     host->agent   Data driven by the host on a write.
  readdata      agent->host   Data returned by the agent on a read.
  byteenable    host->agent   One bit per byte lane; selects which bytes of
                              writedata / readdata are active.
  waitrequest   agent->host   Asserted by the agent to stall the host; the
                              host holds address/data/controls until
                              waitrequest is deasserted (wait-state insertion).
  readdatavalid agent->host   Asserted by the agent when pipelined readdata is
                              valid; used for variable-latency pipelined reads.
  burstcount    host->agent   Number of transfers in a burst.
  chipselect    host->agent   Selects the agent (used by some agents).
  beginbursttransfer host->agent  Marks the first cycle of a burst.
  response      agent->host   Two-bit transfer response (OKAY, RESERVED,
                              SLAVEERROR, DECODEERROR).
  writeresponsevalid agent->host  Qualifies a write response.
  lock          host->agent   Locks an agent for an atomic sequence.
  debugaccess   host->agent   Marks a transfer as a debug access.

2.3 Transfer Properties
-----------------------

Each Avalon-MM interface declares timing properties that the interconnect uses:

  - Address alignment: word addressing (the address increments per word) or
    byte addressing (the address increments per byte). Avalon-MM addresses are
    interpreted as byte addresses by convention but an interface declares its
    addressUnits as words or symbols (bytes).
  - readLatency (fixed read latency): for a fixed-latency pipelined agent, the
    number of cycles after a read is accepted before readdata is valid. A
    readLatency of 0 means readdata is returned combinationally in the same
    cycle.
  - readWaitTime / writeWaitTime: the number of wait-states an agent inserts;
    for waitrequest-controlled agents the wait is signaled dynamically by
    waitrequest instead of by a fixed count.
  - setupTime: address/control setup cycles before read or write is sampled.
  - holdTime: cycles that address/data are held after a transfer.
  - waitrequestAllowance: the number of additional transfers a host may issue
    after waitrequest is asserted before it must stop.
  - burst alignment / maximumPendingReadTransactions: burst and pipeline depth
    limits.

2.4 Transfer Types
------------------

  Slave read/write with waitrequest: the agent asserts waitrequest to insert
  wait-states; the host keeps address, read/write, writedata, and byteenable
  stable until the agent deasserts waitrequest, at which point the transfer
  completes. This is the canonical wait-state-controlled transfer.

  Fixed read latency (pipelined): a read transfer is accepted on the cycle in
  which waitrequest is low; readdata becomes valid exactly readLatency cycles
  later, with no per-transfer readdatavalid required.

  Variable read latency (pipelined with readdatavalid): the agent returns each
  readdata word accompanied by readdatavalid asserted; latency may vary per
  transfer. The host accepts readdata on every cycle that readdatavalid is
  high. Pipelined reads allow multiple reads to be in flight.

  Burst transfers: a host issues burstcount transfers as a single burst. For a
  write burst the host drives writedata on each cycle that waitrequest is low;
  for a read burst the agent returns burstcount words each qualified by
  readdatavalid. beginbursttransfer marks the first cycle of the burst.

2.5 Pipelined Transfers and Backpressure
----------------------------------------

Avalon-MM supports pipelined read transfers: a host may issue further reads
before earlier reads return data. The agent uses readdatavalid to indicate
which cycles carry returned readdata, decoupling the address phase from the
data phase. waitrequest provides backpressure on the address/command phase: an
agent that cannot accept a new command asserts waitrequest, and the host must
hold its command until waitrequest is deasserted.

================================================================================
3. AVALON STREAMING INTERFACE (Avalon-ST)
================================================================================

3.1 Roles
---------

An Avalon-ST interface is either a source (the data producer) or a sink (the
data consumer). The connection is unidirectional and point-to-point: a source
drives data toward a sink. Platform Designer can insert adapters (data-width
adapters, channel adapters, timing adapters) between an incompatible source and
sink.

3.2 Signal Roles
----------------

  data           source->sink  The payload symbols transferred each beat.
  valid          source->sink  Asserted when data (and the other source
                               outputs) are valid this cycle.
  ready          sink->source  Asserted when the sink can accept data; provides
                               backpressure to the source.
  channel        source->sink  Identifies the channel/virtual stream a data
                               beat belongs to (for multiplexed streams).
  error          source->sink  Per-beat error bits describing data errors.
  startofpacket  source->sink  Marks the first beat of a packet (packetized
                               streams only).
  endofpacket    source->sink  Marks the last beat of a packet.
  empty          source->sink  Number of empty (unused) symbols in the final
                               beat of a packet.

3.3 Ready Latency and Backpressure
----------------------------------

The Avalon-ST handshake is the ready/valid pair. The key timing property is
readyLatency: the number of cycles between the sink asserting ready and the
source being permitted to assert valid for an accepted transfer. With a
readyLatency of 0, a transfer occurs on any cycle where both ready and valid
are asserted. With a readyLatency of N, the source may drive valid data on a
cycle if ready was asserted N cycles earlier. Backpressure is the mechanism by
which a sink stalls a source by deasserting ready.

3.4 Packets
-----------

A packetized Avalon-ST interface frames data with startofpacket and
endofpacket. The first beat of a packet asserts startofpacket; the last beat
asserts endofpacket. The empty signal on the final beat indicates how many
symbol lanes are unused. Non-packetized streams omit startofpacket /
endofpacket and simply transfer a continuous stream of symbols qualified by
valid/ready.

3.5 Data Transfer Properties
----------------------------

An Avalon-ST source/sink declares: symbolsPerBeat (symbols transferred per
valid cycle), dataBitsPerSymbol, readyLatency, beatsPerCycle, and whether the
interface is packetized (firstSymbolInHighOrderBits ordering, error width,
channel width, maxChannel).

================================================================================
4. SUPPORTING INTERFACE TYPES
================================================================================

4.1 Avalon Conduit Interface
----------------------------

A Conduit interface groups arbitrary signals that do not fit the
memory-mapped or streaming models. Conduit signals are exported by Platform
Designer to the top level of the system, where they connect to device pins or
to logic outside the generated system. A conduit signal has a user-defined role
and a direction (input, output, or bidir).

4.2 Avalon Interrupt Interface
------------------------------

An interrupt sender (an agent that generates interrupts) drives an irq signal
to an interrupt receiver (typically the processor). The receiver collects irq
lines from multiple senders; Platform Designer assigns each sender an interrupt
number. Individual-requests and receiver-prioritized models are supported.

4.3 Avalon Clock Interface
--------------------------

A Clock interface either outputs a clock (a clock source) or accepts a clock (a
clock sink). Platform Designer connects clock sources to clock sinks and uses
the clock relationships to insert clock-domain-crossing logic where a host and
an agent are in different clock domains.

4.4 Avalon Reset Interface
--------------------------

A Reset interface either outputs a reset (a reset source) or accepts a reset (a
reset sink). Reset can be synchronous or asynchronous; Platform Designer
generates reset synchronizers as required.

4.5 Avalon Memory-Mapped Tristate Conduit Interface (Avalon-TC)
---------------------------------------------------------------

The Tristate Conduit interface carries memory-mapped transfers to off-chip
devices that share tristate bidirectional pins (for example, common flash and
SRAM that multiplex data and address). A tristate conduit host and agent
arbitrate access to the shared tristate signals; Platform Designer generates a
tristate conduit bridge to multiplex multiple off-chip devices onto a shared
bus.

================================================================================
5. INTERCONNECT AND PLATFORM DESIGNER
================================================================================

Platform Designer (Qsys) generates the interconnect that connects Avalon
interfaces. For Avalon-MM the generated interconnect performs:

  - Address decoding: routes a host transfer to the correct agent based on the
    agent's base address.
  - Arbitration: when multiple hosts contend for one agent, a round-robin
    (fairness-based) arbiter grants access; arbitration shares are
    configurable.
  - Data-path multiplexing: muxes readdata from the addressed agent back to the
    requesting host.
  - Width adaptation: adapts between hosts and agents of different data widths
    using byteenable.
  - Burst adaptation: converts bursts between interfaces with different burst
    capabilities.
  - Clock crossing: inserts clock-domain-crossing bridges between interfaces in
    different clock domains.

For Avalon-ST the interconnect is a direct point-to-point connection between a
source and a sink, with optional adapters (data-format, channel, error, and
timing adapters) inserted automatically when properties differ.

================================================================================
6. RELATIONSHIP TO OTHER BUS STANDARDS
================================================================================

Avalon is the native FPGA-SoC interconnect for Intel/Altera Platform Designer.
It is distinct from ARM AMBA AXI (which uses five independent channels with
ARVALID/AWVALID/RVALID/BVALID handshakes and separate read/write address and
data channels), from ARM AMBA AHB (which uses HADDR/HTRANS/HREADY/HRESP with a
pipelined address/data phase), and from the OpenCores point-to-point handshake
bus (a cycle/strobe/acknowledge handshake). Avalon's defining structural
features are the waitrequest wait-state mechanism plus readdatavalid
pipelined-read completion
on Avalon-MM, and the source/sink ready/valid + startofpacket/endofpacket
framing on Avalon-ST. Platform Designer can bridge Avalon to AXI and AHB using
generated bridge components, but the Avalon signaling itself is independent of
those standards.

================================================================================
7. SUMMARY OF KEY PROPERTIES
================================================================================

  - Interface family: Avalon-MM, Avalon-ST, Conduit, Interrupt, Clock, Reset,
    Tristate Conduit (Avalon-TC).
  - Avalon-MM roles: host (master) and agent (slave); address/read/write/
    readdata/writedata/byteenable/waitrequest/readdatavalid/burstcount.
  - Avalon-MM transfers: waitrequest wait-states, fixed read latency, variable
    read latency with readdatavalid, pipelined reads, bursts.
  - Avalon-ST roles: source and sink; data/valid/ready/channel/error/
    startofpacket/endofpacket/empty; readyLatency backpressure; packets.
  - Transfer properties: addressUnits (word vs byte), readLatency, setupTime,
    holdTime, waitrequestAllowance, burst alignment, readyLatency,
    symbolsPerBeat.
  - Used by: Platform Designer / Qsys, Nios II, Quartus Prime.
