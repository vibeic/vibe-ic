Open Core Protocol Specification

OCP-IP Association — Open Core Protocol (OCP) Specification, Release 3.0

1. Introduction and Scope

The Open Core Protocol (OCP) defines a high-performance, bus-independent,
point-to-point interface between two communicating entities such as IP cores
and on-chip bus wrappers. One entity acts as the master and the other as the
slave. Only the master can present commands; it is the controlling entity. The
slave responds to commands presented to it, either by accepting data from the
master or by presenting data to the master. For two entities to communicate in
a peer-to-peer fashion there must be two instances of OCP connecting them — one
where the first entity is a master and the other where the first entity is a
slave.

OCP is a synchronous interface: all OCP signals (other than the reset signal
Reset_n and the optional asynchronous interrupt and error signals) are sampled
on the rising edge of the OCP clock Clk. OCP does not dictate the wordlength of
any data carried by the protocol; the interface is highly configurable. The
characteristics of the IP core determine whether the OCP instance has a simple
or a complex interface.

OCP describes a master/slave interface, organized as a bus-independent socket.
The OCP socket isolates the IP core from the specifics of the on-chip
communication subsystem (the bus or the interconnect). A core that is wrapped
with an OCP interface can be reused with any on-chip bus that provides an OCP
wrapper, because the core only ever talks OCP. The point-to-point synchronous
nature of OCP makes it straightforward to drive timing closure.

OCP signals are divided into three groups:
  - Dataflow signals — the bulk of OCP, carrying the address, command, data,
    and response. Subdivided into basic signals, simple extensions, burst
    extensions, tag extensions, and thread extensions.
  - Sideband signals — additional control, status, and interrupt information
    that flows outside the request/response dataflow. Includes reset.
  - Test signals — support for scan, JTAG (IEEE 1149.1), and clock control.

The OCP-IP Association maintains the specification; the OCP-IP work was
subsequently contributed to Accellera Systems Initiative. OCP is used as a core
interface socket (the OCP socket).

2. Theory of Operation — Phases and the Dataflow Model

An OCP transfer is decomposed into phases. Each OCP transfer has a request
phase and (for commands that read or that require a response) a response phase.
A transfer with write data that is sent separately from the request uses a
datahandshake phase.

  - Request phase: the master drives the request group (MCmd, MAddr, MData for
    a write that does not use datahandshake, MByteEn, plus any burst/tag/thread
    qualifiers) and asserts a valid command on MCmd. The slave accepts the
    request by asserting SCmdAccept. The request phase ends on the rising clock
    edge where MCmd is valid and SCmdAccept is asserted (the request handshake).
  - Datahandshake phase: when the datahandshake extension is configured, write
    data is transferred in a separate phase using MDataValid (master asserts
    write data is valid), MData / MDataByteEn, and SDataAccept (slave accepts
    the write data). This decouples the write command from the write data and
    is required for write bursts that pipeline data behind the address.
  - Response phase: for read commands (and for writes that request a response)
    the slave drives the response group — SResp (the response code), SData (the
    read data), plus any tag/thread qualifiers — and the master accepts the
    response by asserting MRespAccept. The response phase ends on the rising
    clock edge where SResp is non-NULL and MRespAccept is asserted.

Flow control is provided by the accept signals: SCmdAccept gates the request
phase, SDataAccept gates the datahandshake phase, and MRespAccept gates the
response phase. When the corresponding accept signal is not configured, the
phase completes in a single cycle with no wait state.

3. Dataflow Signals

3.1 Basic signals (always present)

  - Clk          — input clock. All OCP signals are synchronous to the rising
                   edge of Clk (except Reset_n / interrupt / error).
  - EnableClk    — qualifies which rising edges of Clk are active OCP edges.
  - MAddr        — master address. The transfer address, configurable width
                   addr_wdth. Aligned to the OCP word.
  - MCmd         — master command. A 3-bit field encoding the request:
                   IDLE, WR (write), RD (read), RDEX (read exclusive),
                   RDL (read linked), WRNP (write non-post), WRC (write
                   conditional), BCST (broadcast).
  - MData        — master (write) data, configurable width data_wdth.
  - MDataValid   — master write-data valid (datahandshake extension).
  - MRespAccept  — master accepts the response presented by the slave.
  - SCmdAccept   — slave accepts the request presented by the master.
  - SData        — slave (read) data returned to the master.
  - SDataAccept  — slave accepts the write data (datahandshake extension).
  - SResp        — slave response. A 2-bit field encoding the response:
                   NULL (no response), DVA (data valid / command accepted),
                   FAIL (request failed), ERR (response error).

3.2 Simple extension signals

  - MAddrSpace   — master address space (selects a region / address space).
  - MByteEn      — master byte enables; selects which bytes of MData/SData of
                   the OCP word are part of the transfer.
  - MDataByteEn  — master data byte enables for the datahandshake phase.
  - MDataInfo    — extra information sent with the write data (e.g. parity).
  - SDataInfo    — extra information sent with the read data.
  - MReqInfo     — extra information sent with the request.
  - SRespInfo    — extra information sent with the response.

3.3 Burst extension signals

OCP supports bursts. A burst is a set of transfers that are linked together
into a single transaction. Bursts can be precise (the burst length is known and
declared up front in MBurstLength) or imprecise (the burst length is presented
incrementally and the last transfer is marked by MReqLast / MDataLast). Burst
sequences (MBurstSeq) include:
  - INCR  — incrementing address burst.
  - WRAP  — wrapping address burst (cache-line style wrap-around).
  - STRM  — streaming burst (constant address; FIFO-style).
  - XOR   — XOR address sequence (critical-word-first cache fill).
  - UNKN  — unknown / user-defined address sequence.
  - DFLT1 / DFLT2 — user-defined default sequences.
And 2-dimensional block bursts (BLCK) for image / DMA tiling.

Burst signals:
  - MBurstLength   — the length of the burst (number of words).
  - MBurstSeq      — the address sequence of the burst (INCR/WRAP/STRM/XOR/...).
  - MBurstPrecise  — distinguishes precise from imprecise bursts.
  - MBurstSingleReq — single-request burst (one request, many data transfers).
  - MReqLast       — marks the last request of an imprecise burst.
  - MDataLast      — marks the last write-data word of a burst.
  - SRespLast      — marks the last response of a burst.
  - MReqRowLast / MDataRowLast / SRespRowLast — 2D-block-burst row markers.
  - MBlockHeight / MBlockStride — 2D-block-burst geometry.
  - MAtomicLength  — atomic transfer length (atomicity within a burst).

3.4 Tag extension signals

Tags allow responses to return out of order with respect to the requests that
generated them within a single thread. The tag identifies which request a
response corresponds to.
  - MTagID    — master tag identifier on the request.
  - STagID    — slave tag identifier on the response.
  - MTagInOrder / STagInOrder — force in-order handling for a tagged transfer.

3.5 Thread extension signals

Threads provide concurrency: each thread is an independent flow of transfers,
and transfers on different threads have no ordering requirement with respect to
one another. Threads enable out-of-order responses across threads and pipelined
concurrency.
  - MThreadID  — master thread identifier (selects the request thread).
  - SThreadID  — slave thread identifier (selects the response thread).
  - MConnID    — master connection identifier (the initiator connection).
  - SThreadBusy / MThreadBusy — per-thread busy (flow-control hint that a
                   given thread cannot currently accept a transfer).
  - MDataThreadBusy — per-thread busy for the datahandshake phase.

4. Sideband Signals

Sideband signals carry control, status, interrupt, error, and reset
information that is not part of the dataflow handshake.
  - Control / ControlBusy / ControlWr — generic master->slave control register.
  - Status / StatusBusy / StatusRd     — generic slave->master status register.
  - MError / SError                     — error indication.
  - MFlag / SFlag                       — generic master / slave sideband flags.
  - SInterrupt                          — slave-to-master interrupt request.
  - MReset_n / SReset_n / Reset_n       — reset (active low). Reset_n is the
                                          asynchronous OCP reset; the OCP
                                          interface is held in its idle state
                                          while Reset_n is asserted.
  - ConnID-based connection management and the OCP connection model.

5. Test Signals

Test signals provide design-for-test access:
  - Scan signals — Scanctrl, Scanin, Scanout for scan-chain DFT.
  - JTAG signals — TCK, TMS, TDI, TDO, TRST_N per IEEE 1149.1 boundary scan.
  - ClkByp / TestClk — clock-control / clock-bypass for at-speed test.

6. Configuration and the OCP Socket

OCP is highly configurable: an OCP interface instance only carries the signals
that the connected IP core needs. The configuration is expressed as a set of
parameters (the RTL configuration), for example:
  - addr_wdth       — width of MAddr (address bus width).
  - data_wdth       — width of MData / SData (data bus width).
  - addrspace_wdth  — width of MAddrSpace.
  - byteen          — whether MByteEn is present.
  - mthreadid_width — width of MThreadID (number of threads).
  - sthreadid_width — width of SThreadID.
  - tags            — number of tags (width of MTagID / STagID).
  - connid_wdth     — width of MConnID.
  - burstlength     — whether bursts are enabled and the burst-length field.
  - datahandshake   — whether the separate datahandshake phase is present.
  - readex_enable / writeresp_enable / rdlwrc_enable — which commands are legal.
  - sdatainfo_wdth / mdatainfo_wdth / reqinfo_wdth / respinfo_wdth — info widths.

A profile is a named, pre-agreed bundle of OCP configuration parameters that
masters and slaves use to interoperate (for example a "block data flow"
profile, a "register access" profile, or a "sequential undefined-length data
flow" profile). The socket is the complete set of OCP signals on one side of
the interface.

7. Command Encoding (MCmd, 3-bit)

  0  IDLE  — no request this cycle.
  1  WR    — write.
  2  RD    — read.
  3  RDEX  — read exclusive (locks for atomic read-modify-write).
  4  RDL   — read linked (load-linked, pairs with WRC store-conditional).
  5  WRNP  — write non-posted (a response is returned).
  6  WRC   — write conditional (store-conditional).
  7  BCST  — broadcast.

8. Response Encoding (SResp, 2-bit)

  0  NULL  — no response (slave is idle / no data this cycle).
  1  DVA   — data valid / accept (read data valid, or write accepted).
  2  FAIL  — request failed (e.g. exclusive access lost).
  3  ERR   — response error (the request could not be serviced).

9. Register-style Sideband Access (Control / Status)

The Control and Status sideband registers provide a generic out-of-band
register window. A master writes the Control register (ControlWr) and reads the
Status register (StatusRd); ControlBusy / StatusBusy provide flow control on
these accesses. These are distinct from the dataflow MAddr-addressed register
space and are used for slow configuration / status that does not need the full
dataflow bandwidth.

10. Worked Transaction Examples

10.1 Single read
  Cycle 1: master drives MCmd=RD, MAddr=A; slave asserts SCmdAccept -> request
           handshake completes.
  Cycle n: slave drives SResp=DVA, SData=D; master asserts MRespAccept ->
           response handshake completes.

10.2 Single write (no datahandshake)
  Cycle 1: master drives MCmd=WR, MAddr=A, MData=D, MByteEn; slave asserts
           SCmdAccept -> the write is accepted (posted write, no response).

10.3 Non-posted write (WRNP)
  Cycle 1: master drives MCmd=WRNP, MAddr=A, MData=D; SCmdAccept asserted.
  Cycle n: slave drives SResp=DVA (write accepted); MRespAccept asserted.

10.4 Burst read (precise INCR, single request)
  Cycle 1: MCmd=RD, MAddr=A, MBurstLength=4, MBurstSeq=INCR,
           MBurstSingleReq=1; SCmdAccept asserted.
  Cycles: slave returns 4 response beats, each SResp=DVA, SData, with
          SRespLast asserted on the 4th; master asserts MRespAccept each beat.

10.5 Write burst with datahandshake
  Request: MCmd=WR, MAddr=A, MBurstLength=4, MBurstSeq=INCR; SCmdAccept.
  Data:    four MDataValid beats, MData / MDataByteEn, MDataLast on the 4th;
           each accepted by SDataAccept.

11. Connection, Threads, and Out-of-Order

Within a single thread, transfers complete in order unless tags are used to
permit out-of-order responses. Across threads (selected by MThreadID /
SThreadID) there is no ordering constraint, so a slave may return responses for
different threads in any interleaving. MConnID identifies the initiator
connection for systems that need to track which master a request came from
(quality-of-service, security, routing). SThreadBusy / MThreadBusy allow a
receiver to back-pressure individual threads without stalling the whole socket.

12. Relationship to System Buses

OCP is bus-independent: the IP core sees only the OCP socket, and a bus wrapper
translates between OCP and the on-chip interconnect. This is in contrast to a
bus-specific interface that is hard-wired to one interconnect. Because the OCP
master always issues MCmd and consumes SResp, and the OCP slave always asserts
SCmdAccept and issues SResp/SData, the same core can be moved between systems by
swapping only the bus wrapper. The M-prefixed signals are always driven by the
master; the S-prefixed signals are always driven by the slave.
