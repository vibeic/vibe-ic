IO-Link Interface and System Specification — Single-drop Digital Communication Interface (SDCI)
IEC 61131-9 (SDCI — Single-drop Digital Communication Interface for small sensors and actuators)

ABSTRACT

IO-Link is a point-to-point, serial, digital communication interface for
connecting individual sensors and actuators to an IO-Link Master. It is
standardized internationally as IEC 61131-9 under the name SDCI
(Single-drop Digital Communication Interface). IO-Link is NOT a fieldbus and
is NOT a bus: each IO-Link Device is connected point-to-point to one port of
an IO-Link Master over a single unshielded three-wire cable (maximum 20 m).
The three wires are L+ (24 V supply), L- (ground / 0 V return), and C/Q
(the combined communication and switching signal line). The C/Q line is the
single signal wire that carries either a digital switching signal in
Standard IO (SIO) mode or the serial UART communication frames in SDCI
(communication) mode.

IO-Link reuses a UART-based, half-duplex serial framing: each UART character
is one start bit, eight data bits, one even parity bit, and one stop bit
(8-E-1, 11 bits per character). Three transmission rates are defined: COM1 =
4.8 kbaud, COM2 = 38.4 kbaud, and COM3 = 230.4 kbaud. A Device supports
exactly one of the three COM rates; the Master detects the Device's COM rate
during wake-up. The Master initiates communication with a wake-up request
(a defined pulse on the C/Q line) that switches the Device from SIO
(Standard IO) mode into SDCI (communication) mode. After communication is
established, the Master and Device exchange M-sequences (message sequences):
each M-sequence is a Master message followed by a Device response. Data
integrity is protected by a checksum (the CKT byte in the Master message and
the CKS byte in the Device response).

IO-Link transports three kinds of data: cyclic Process Data (PD, up to 32
bytes per direction), acyclic On-request Data accessed through the ISDU
(Indexed Service Data Unit) service using an Index and Subindex, and Events
(diagnostic notifications). Each Device is described by an IODD (IO Device
Description), an XML file that the engineering tool uses to identify and
parameterize the Device. The Device moves through defined states
(startup / preoperate / operate), driven by the MasterCommand, and each
Device declares a minimum cycle time the Master must respect.

This document specifies the SDCI physical interface (L+, L-, C/Q), the SIO
and SDCI modes, the wake-up procedure, the UART character framing and the
COM1/COM2/COM3 rates, the M-sequence message format and the CKT/CKS
checksums, the Process Data and On-request Data (ISDU) services, the Event
mechanism, the IODD, the Device state machine, and the timing.

1. OVERVIEW

IO-Link (IEC 61131-9, SDCI) defines how a single sensor or actuator (the
IO-Link Device) communicates with one port of an IO-Link Master. The link is
strictly point-to-point: one Device per Master port, connected by a single
three-wire cable. There is no multi-drop, no bus topology, and no addressing
of multiple Devices on one line — the IO-Link Master provides multiple
independent ports, and each port drives exactly one Device.

The Master is always the communication master: it initiates every exchange.
The Device is the communication slave: it only answers when the Master
addresses it. This Master/Device (master/slave) relationship is fundamental
to SDCI and distinguishes IO-Link from a peer-to-peer or multi-master bus.

The physical interface uses three wires per port:
  - L+  : 24 V DC supply to the Device (nominal 24 V, the device power line).
  - L-  : ground / 0 V supply return (common reference).
  - C/Q : the Combined Communication and switching signal line. This single
          signal wire is the heart of IO-Link. In Standard IO (SIO) mode it
          carries a binary switching signal (like an ordinary digital sensor
          output, a DI/DO line). In SDCI (communication) mode it carries the
          serial UART communication frames between Master and Device.

Because the C/Q line is dual-purpose, an IO-Link Device is fully backward
compatible with a conventional binary (SIO) sensor: when no IO-Link Master
is present, or before communication is established, the Device operates in
SIO mode and the C/Q line behaves as a standard switching output. When an
IO-Link Master is connected, it issues a wake-up request to switch the
Device into SDCI (communication) mode.

A second optional Device output, Q (also called the additional
digital-output/digital-input on pin 2 of a standard M12 connector), may be
present, but the defining IO-Link signal is the C/Q line on which the
SDCI communication runs.

2. PHYSICAL LAYER AND WIRING

2.1 Three-wire interface

Every IO-Link port presents three wires: L+, L-, and C/Q. On a standard M12
A-coded connector these map to pin 1 (L+), pin 3 (L-), and pin 4 (C/Q);
pin 2 may carry the optional Q line. The cable is an unshielded standard
three-wire (or five-wire) sensor cable, maximum length 20 m. No special
shielded or twisted cable is required, which keeps IO-Link inexpensive.

2.2 C/Q line signaling

The C/Q line is push-pull driven between the low level (near L-, 0 V) and
the high level (near L+, 24 V). In SIO mode the level directly represents the
switching state. In SDCI mode the line carries UART characters: the idle
level corresponds to the UART idle (logic 1), each character starts with a
falling edge (the start bit), and the bits are clocked at the negotiated COM
rate.

2.3 Supply

L+ supplies up to 24 V to the Device; L- is the return. The Device draws its
operating current from L+/L-. There is no separate communication power; the
C/Q communication shares the same ground reference as the supply.

3. SIO MODE AND SDCI MODE

3.1 SIO (Standard IO) mode

In Standard IO (SIO) mode the C/Q line behaves like a conventional binary
sensor signal: a digital switching output (or input). A Device powers up in
SIO mode and remains there until an IO-Link Master wakes it up. SIO mode lets
an IO-Link Device be used with a plain digital input card when no IO-Link
Master is available.

3.2 SDCI (communication) mode

In SDCI (Single-drop Digital Communication Interface) mode the C/Q line
carries the serial IO-Link communication: UART frames organized into
M-sequences. The Device enters SDCI mode only after the Master's wake-up
request. While in SDCI mode the cyclic exchange of Process Data and the
acyclic exchange of On-request Data take place.

3.3 Mode transition

The transition SIO -> SDCI is triggered by the wake-up request from the
Master. The reverse transition SDCI -> SIO occurs on a fallback (the Master
issues a Fallback MasterCommand, or communication is lost), returning the
C/Q line to the binary switching behavior.

4. WAKE-UP PROCEDURE

4.1 Wake-up request

To start communication the Master applies a wake-up request (WURQ) on the
C/Q line: a defined wake-up current/voltage pulse of specified width. The
Device, which is in SIO mode, detects the wake-up pulse and switches into
SDCI communication mode, preparing to receive the first UART character from
the Master.

4.2 COM-rate detection

A Device supports exactly one transmission rate — COM1, COM2, or COM3. After
the wake-up request the Master attempts communication; it tries the COM rates
to find the one the Device answers on. Once the Master receives a valid
Device response it has detected the Device's COM rate and proceeds.

4.3 Establishing communication

After wake-up and COM-rate detection the Master reads the Device's
identification (the Direct Parameter page: VendorID, DeviceID, and protocol
parameters such as the minimum cycle time and the Process Data lengths), then
drives the Device through its state machine toward the OPERATE state.

5. UART CHARACTER FRAMING

5.1 Character format

Each IO-Link UART character is transmitted as:
  - 1 start bit (logic 0, the falling edge that begins the character),
  - 8 data bits (least significant bit first),
  - 1 even parity bit,
  - 1 stop bit (logic 1).
This is the 8-E-1 format: 11 bit times per character. The even parity bit is
chosen so that the total number of 1 bits in the 8 data bits plus the parity
bit is even.

5.2 Transmission rates

Three COM rates are defined:
  - COM1 = 4.8 kbaud   (bit time approx. 208.33 us)
  - COM2 = 38.4 kbaud  (bit time approx. 26.04 us)
  - COM3 = 230.4 kbaud (bit time approx. 4.34 us)
A Device implements one of these; the Master adapts to the Device's rate.
Higher COM rates give shorter cycle times.

5.3 Half-duplex

Communication is half-duplex on the single C/Q line: the Master transmits its
message, then the Device transmits its response. The two never transmit
simultaneously; the line direction reverses between the Master message and
the Device response within each M-sequence.

6. M-SEQUENCES (MESSAGE SEQUENCES)

6.1 Structure

Communication in SDCI mode is organized into M-sequences (message
sequences). Each M-sequence consists of:
  - a Master message: a Master Control octet (MC) selecting read/write and an
    address/communication channel, optionally followed by Process Data and/or
    On-request Data octets, terminated by a checksum octet CKT.
  - a Device response: optional Process Data and/or On-request Data octets,
    a status octet, terminated by a checksum octet CKS.

The Master Control (MC) octet encodes the direction (read/write), the
communication channel (Process, Page, Diagnosis, ISDU), and the address.

6.2 M-sequence types

The number of octets in the Master message and Device response depends on the
M-sequence TYPE:
  - TYPE_0 : a single On-request Data octet per message (used in STARTUP).
  - TYPE_1 : an On-request Data octet plus a small fixed Process Data length.
  - TYPE_2 : interleaved or larger Process Data with On-request Data, used in
    OPERATE for Devices with longer Process Data.
The M-sequence type and the Process Data lengths are taken from the Device's
Direct Parameter page during STARTUP.

6.3 Checksums (CKT and CKS)

Each Master message ends with a checksum octet CKT, and each Device response
ends with a checksum octet CKS. The checksum is a 6-bit checksum combined
with a 2-bit type/event field, computed over the message octets, providing
data-integrity protection over the half-duplex link. A checksum mismatch
causes the receiver to discard the message and the Master to retry.

7. PROCESS DATA (CYCLIC)

7.1 Process Data

Process Data (PD) is the cyclic, real-time data exchanged every cycle: the
Device's measured value (Process Data In, from Device to Master) and the
actuator setpoint (Process Data Out, from Master to Device). Process Data is
exchanged automatically in the OPERATE state without an explicit request.

7.2 Process Data length

The Process Data length is fixed for a given Device and declared in its
Direct Parameter page / IODD. Process Data may be up to 32 bytes per
direction. Short Devices use a few bits or one or two bytes; complex Devices
use up to the 32-byte maximum.

7.3 Cyclic exchange and minimum cycle time

In OPERATE the Master polls the Device every cycle, exchanging Process Data
in each M-sequence. Each Device declares a Minimum Cycle Time (MinCycleTime)
the Master must respect; the Master uses a cycle time greater than or equal to
the Device's minimum. Typical minimum cycle times range from about 0.4 ms to
several ms depending on the COM rate and Process Data length.

8. ON-REQUEST DATA AND ISDU

8.1 On-request Data

On-request Data is acyclic data exchanged only when requested: device
parameters, identification, and diagnostic information. It does not occur
every cycle; it is interleaved with the cyclic Process Data when the
application needs it, so it does not disturb the real-time Process Data.

8.2 ISDU (Indexed Service Data Unit)

Acyclic parameters are accessed through the ISDU (Indexed Service Data Unit)
service. An ISDU request addresses a parameter by an Index (16-bit) and an
optional Subindex (8-bit). The Master sends an ISDU read or write request;
the Device returns the parameter value or an acknowledgement. Because an ISDU
can be larger than a single M-sequence payload, it is segmented across
several M-sequences and reassembled. Standard Index values are defined
(e.g. Index 0x0010 VendorName, 0x0012 ProductName, 0x0018 ApplicationSpecific
Tag), and vendor-specific Index ranges are available.

8.3 Direct Parameter page

The Direct Parameter page (Page 1) holds the core communication parameters —
MasterCommand, MasterCycleTime, MinCycleTime, M-sequence capability,
RevisionID, VendorID, DeviceID, FunctionID — and is read directly (not via
ISDU) during STARTUP so the Master can configure the link before entering
OPERATE.

9. EVENTS (DIAGNOSTICS)

The Device reports diagnostic information through Events. An Event carries an
EventCode, an EventQualifier (mode: appears/disappears/single-shot; type:
notification/warning/error; source: device/master), and is signalled by the
Device in its response so the Master can read the Event detail. Events let a
Device announce error conditions (over-temperature, short circuit, parameter
error) without polling, improving diagnostics over a plain binary sensor.

10. DEVICE STATES AND MASTERCOMMAND

10.1 Device state machine

An IO-Link Device moves through the following states:
  - STARTUP    : after wake-up, the Master reads the Direct Parameter page
    (identification, MinCycleTime, Process Data lengths, M-sequence type) and
    checks the Device identity.
  - PREOPERATE : the Master parameterizes the Device via ISDU (writes device
    parameters, reads back identification) before cyclic data exchange.
  - OPERATE    : cyclic Process Data exchange is active; On-request Data and
    Events are interleaved as needed.

10.2 MasterCommand

The Master drives the state transitions with the MasterCommand (a value in
the Direct Parameter page): commands such as Fallback (return to SIO),
MasterIdent, DeviceIdent, PreoperateMaster (enter PREOPERATE), and
OperateMaster (enter OPERATE). The Device executes the MasterCommand and
moves to the corresponding state.

10.3 Fallback

A Fallback MasterCommand (or a communication loss) returns the Device to SIO
mode: the C/Q line resumes its binary switching behavior.

11. IODD (IO DEVICE DESCRIPTION)

Each IO-Link Device is accompanied by an IODD (IO Device Description), an XML
file provided by the Device vendor. The IODD describes the Device's identity
(VendorID, DeviceID, product name), its Process Data structure, its
parameters (the ISDU Index/Subindex map with data types, ranges, and default
values), its Events, and its communication properties (COM rate, MinCycleTime,
M-sequence type, Process Data lengths). The engineering tool imports the IODD
to identify the Device and to present its parameters to the user. The IODD is
the machine-readable contract between the Device and the engineering
environment; it is XML-based and references vendor logos and Device images.

12. TIMING

12.1 Bit and character timing

The bit time is the reciprocal of the COM rate (208.33 us at COM1, 26.04 us
at COM2, 4.34 us at COM3). A UART character is 11 bit times (8-E-1).

12.2 Cycle timing

The cycle time is the period of the cyclic Process Data exchange. The Master
respects the Device's MinCycleTime. The MasterCycleTime (in the Direct
Parameter page) sets the actual cycle the Master uses.

12.3 Timeouts and retries

The Master applies a response timeout (T_A) after each Master message; if the
Device does not respond within the timeout, or the CKS checksum is wrong, the
Master retries. Repeated failure causes the Master to declare the Device lost
and fall back to SIO.

13. ERROR HANDLING

IO-Link detects errors by:
  - the even parity bit per UART character,
  - the CKT/CKS checksum per M-sequence,
  - response timeouts,
  - and Device-reported Events (diagnostics).
On a checksum or parity error the receiver discards the message and the Master
retries; on repeated failure the Master falls back to SIO mode and may report
a communication-lost Event.

14. ROLES AND TOPOLOGY SUMMARY

  - IO-Link Master : the communication master; provides one or more ports;
    initiates wake-up; drives M-sequences; runs the Device state machine;
    presents Process Data, On-request Data, and Events to the upper fieldbus
    or controller. The Master is the only initiator.
  - IO-Link Device : the communication slave (sensor or actuator); answers
    Master messages; provides Process Data; serves ISDU parameter requests;
    raises Events; is described by an IODD.
  - Topology : strictly point-to-point, one Device per Master port, single
    three-wire cable (L+, L-, C/Q), maximum 20 m, unshielded. Not a fieldbus,
    not a bus, no multi-drop, no Device addressing on the wire.

15. RELATIONSHIP TO SIBLINGS

IO-Link reuses UART character framing (8-E-1) but is NOT a plain UART link: a
plain UART link has only asynchronous start/stop framing on TX/RX wires and
no C/Q dual-mode line, no wake-up request, no SIO<->SDCI mode switch, no
M-sequences, and no ISDU. IO-Link is also not SENT (SAE J2716): SENT encodes
data as nibble pulse widths in ticks on a single wire with a 56-tick
calibration pulse, whereas IO-Link uses standard UART octets at COM1/COM2/COM3
with M-sequence framing and CKT/CKS checksums. The defining IO-Link signature
is the SDCI single-drop point-to-point link on the C/Q combined communication
and switching line, with the wake-up request switching SIO mode to SDCI mode,
M-sequences with CKT/CKS checksums at COM1/COM2/COM3, cyclic Process Data,
acyclic On-request Data via ISDU Index/Subindex, Events, and the IODD.

16. SUMMARY OF KEY FACTS

  - Standard: IEC 61131-9, SDCI (Single-drop Digital Communication Interface).
  - Point-to-point, one Device per Master port; NOT a fieldbus, NOT a bus.
  - Three wires: L+ (24 V), L- (ground), C/Q (combined communication and
    switching signal line).
  - UART 8-E-1 (1 start, 8 data, 1 even parity, 1 stop); COM1 = 4.8 kbaud,
    COM2 = 38.4 kbaud, COM3 = 230.4 kbaud.
  - Wake-up request switches the Device from SIO (Standard IO) mode to SDCI
    (communication) mode.
  - M-sequences: Master message + Device response, TYPE_0 / TYPE_1 / TYPE_2,
    with CKT (Master) and CKS (Device) checksums.
  - Process Data (cyclic, up to 32 bytes) + On-request Data (acyclic) via ISDU
    (Indexed Service Data Unit, Index/Subindex) + Events (diagnostics).
  - Device states: STARTUP / PREOPERATE / OPERATE, driven by MasterCommand.
  - MinCycleTime declared per Device; Master respects it.
  - IODD (IO Device Description), an XML file, identifies and parameterizes
    the Device.
