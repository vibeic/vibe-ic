LoRa Physical Layer and LoRaWAN Specification (Low-Power Wide-Area Network)

   Document   : LoRa / LoRaWAN Modem and MAC Specification
   PHY source : Semtech LoRa Chirp Spread Spectrum (CSS) Modulation
   MAC source : LoRa Alliance LoRaWAN L2 1.0.4 / Regional Parameters
   Revision   : 1.0.4
   Date       : 2020
   Prepared by: LoRa Alliance Technical Committee
   Scope      : End-device modem (LoRa PHY) + LoRaWAN MAC for low-power,
                long-range, sub-GHz star-of-stars IoT networks.

================================================================================
1. ABSTRACT
================================================================================

This specification defines a low-power wide-area network (LPWAN) built from two
layers: the LoRa physical layer (PHY), a proprietary Semtech Chirp Spread
Spectrum (CSS) modulation operating in the sub-GHz ISM bands, and the LoRaWAN
medium-access-control (MAC) layer standardized by the LoRa Alliance. LoRa CSS
trades data rate for link budget: by spreading a low-rate payload across a wide
RF chirp it achieves very high receiver sensitivity (down to about -148 dBm) and
long range (several to >15 km) at milliwatt transmit power, enabling battery
lifetimes measured in years. LoRaWAN organizes end-devices, gateways, and a
network server into a star-of-stars topology, defines device Classes A/B/C,
over-the-air (OTAA) and by-personalization (ABP) activation, adaptive data rate
(ADR), duty-cycle-limited channel access, and per-frame integrity (MIC) and
encryption based on AES-128.

3. LORA PHYSICAL LAYER (SEMTECH CSS MODULATION)
================================================================================

3.1 Chirp Spread Spectrum (CSS)
-------------------------------
The LoRa PHY uses Chirp Spread Spectrum (CSS) modulation. A LoRa symbol is a
linear frequency chirp that sweeps across the entire channel bandwidth. Each
symbol encodes SF bits of information by the cyclic starting frequency (time
offset) of the chirp; an up-chirp sweeps from low to high frequency, a
down-chirp from high to low. CSS spreads the signal energy over a wide
bandwidth, providing strong immunity to interference, multipath, and Doppler,
and allowing demodulation below the noise floor. The processing gain of CSS is
what gives LoRa its long range and high link budget.

3.2 Spreading Factor (SF7-SF12)
-------------------------------
The Spreading Factor (SF) sets the number of raw bits carried per symbol and the
chirp duration. LoRa supports SF7, SF8, SF9, SF10, SF11, and SF12. A symbol of
spreading factor SF contains 2^SF chips and carries SF bits. Higher SF means a
longer symbol (lower data rate), more processing gain, higher receiver
sensitivity, and longer range, at the cost of longer time-on-air and higher
energy per frame. Lower SF means shorter symbols, higher data rate, and shorter
range. Symbol duration Tsym = 2^SF / BW.

3.3 Bandwidth
-------------
LoRa channels use a bandwidth (BW) of 125 kHz, 250 kHz, or 500 kHz. Most
sub-GHz LoRaWAN uplink channels use 125 kHz. A wider bandwidth gives a higher
data rate (shorter symbol time) but a lower link budget. The symbol rate is
Rsym = BW / 2^SF symbols per second; the chip rate equals the bandwidth (Rc =
BW chips/s).

3.4 Coding Rate (Forward Error Correction)
------------------------------------------
LoRa applies a cyclic forward-error-correction (FEC) code with a coding rate
(CR) of 4/5, 4/6, 4/7, or 4/8. A coding rate of 4/5 adds one parity bit per
four data bits (lowest overhead); 4/8 adds four parity bits per four data bits
(strongest protection, highest overhead). The effective bit rate is
Rb = SF * (BW / 2^SF) * CR.

3.5 Frame Structure: Preamble + Sync Word + Header + Payload + CRC
------------------------------------------------------------------
A LoRa PHY frame consists of:
  - Preamble: a programmable number of up-chirps (default 8 symbols) used by the
    receiver to detect and synchronize to the signal.
  - Sync word: network-identifying symbols following the preamble. A public
    LoRaWAN network uses sync word 0x34; a private network uses 0x12. The sync
    word lets a receiver ignore frames from foreign networks.
  - Start-of-frame delimiter: 2.25 down-chirps marking the end of the preamble.
  - Optional explicit header: carries payload length, coding rate, and a header
    CRC. In implicit-header mode these are fixed and omitted.
  - Payload: the PHY payload (the LoRaWAN frame).
  - Payload CRC: 16-bit CRC appended on uplinks for error detection.

3.6 RF Bands and Link Budget
----------------------------
LoRa operates in the license-free sub-GHz ISM bands. Regional plans include
EU868 (863-870 MHz) and US915 (902-928 MHz), among others (AS923, AU915,
IN865, KR920, CN470). The combination of CSS processing gain, narrow bandwidth,
and high coding rate yields a link budget of about 154 dB and receiver
sensitivity to roughly -148 dBm at SF12/125 kHz, supporting ranges of several
kilometers in urban areas and >15 km in line-of-sight rural deployments.

3.7 Data Rate Table (LoRaWAN EU868 example)
-------------------------------------------
  DR0  : SF12 / 125 kHz  ~   250 bit/s   (longest range)
  DR1  : SF11 / 125 kHz  ~   440 bit/s
  DR2  : SF10 / 125 kHz  ~   980 bit/s
  DR3  : SF9  / 125 kHz  ~  1760 bit/s
  DR4  : SF8  / 125 kHz  ~  3125 bit/s
  DR5  : SF7  / 125 kHz  ~  5470 bit/s
  DR6  : SF7  / 250 kHz  ~ 11000 bit/s   (highest range/rate trade)

4. LORAWAN MAC LAYER (LoRa Alliance)
================================================================================

4.1 Network Architecture (Star-of-Stars)
----------------------------------------
A LoRaWAN network is a star-of-stars. End-devices are not associated with a
single gateway; instead each uplink transmitted by an end-device is received by
every gateway in range and forwarded to a central network server. The network
server deduplicates frames, performs security checks, runs adaptive data rate,
and selects a single gateway for any downlink. The roles are:
  - End-device: a battery-powered sensor/actuator running the LoRa PHY + LoRaWAN
    MAC. It initiates communication.
  - Gateway (concentrator): a transparent bridge that relays LoRa frames between
    end-devices (RF) and the network server (IP backhaul). It performs no MAC.
  - Network server: the network's brain — frame dedup, MAC commands, ADR, frame
    counter checks, MIC verification with the network session key, gateway
    selection for downlinks.
  - Join server: handles the OTAA join procedure and derives session keys.
  - Application server: handles application payload encryption/decryption with
    the application session key and the end-user application logic.

4.2 Device Classes A / B / C
----------------------------
Every LoRaWAN end-device implements Class A; Class B and Class C are optional
extensions that change the downlink-reception behavior:
  - Class A (mandatory, lowest power): each uplink is followed by exactly two
    short downlink receive windows (RX1, RX2). The server can only send a
    downlink during those windows. The device sleeps the rest of the time.
    Bidirectional, end-device-initiated, lowest power consumption.
  - Class B (beacon, scheduled): in addition to Class A windows, the device
    opens scheduled "ping slot" receive windows synchronized to a periodic
    gateway beacon, allowing the server to initiate downlinks with bounded
    latency. Requires a time-synchronizing beacon.
  - Class C (continuous): the device keeps its receiver open continuously
    (except when transmitting), giving the lowest downlink latency at the cost
    of the highest power consumption. Used by mains-powered actuators.

4.3 Activation: OTAA and ABP
----------------------------
A device must obtain a network session context before sending application data.
Two activation methods are defined:

  Over-The-Air Activation (OTAA): the preferred method. The device is
  provisioned with:
    - DevEUI   : 64-bit globally unique device identifier (IEEE EUI-64).
    - JoinEUI  : 64-bit join-server identifier (formerly AppEUI).
    - AppKey   : 128-bit AES root key (and in 1.1 a NwkKey).
  The device sends a Join-Request (DevEUI, JoinEUI, DevNonce). The join server
  validates it and returns a Join-Accept (DevAddr, network settings, AppNonce).
  Both ends then derive:
    - DevAddr  : 32-bit device address within the network.
    - NwkSKey  : 128-bit network session key (MIC + MAC-command security).
    - AppSKey  : 128-bit application session key (payload encryption).

  Activation By Personalization (ABP): the DevAddr, NwkSKey, and AppSKey are
  pre-provisioned directly into the device at manufacture; no join exchange
  occurs. Simpler but less secure (no fresh session keys, static keys).

4.4 Frame Format (MAC Layer)
----------------------------
A LoRaWAN MAC frame (PHYPayload) is:
    MHDR | MACPayload | MIC
where:
  - MHDR (1 byte): MType (frame type: Join-Request, Join-Accept, Unconfirmed/
    Confirmed Data Up/Down, Rejoin) and Major version.
  - MACPayload = FHDR | FPort | FRMPayload
      - FHDR = DevAddr (4 B) | FCtrl (1 B) | FCnt (2 B) | FOpts (0-15 B)
          - FCtrl contains the ADR bit, ADRACKReq, ACK, and FOptsLen.
          - FCnt is the 16-bit (LSB of a 32-bit) frame counter, incremented per
            frame; the server tracks it to detect replays and lost frames.
          - FOpts carries piggybacked MAC commands.
      - FPort (1 B): 0 for MAC-command-only frames, 1-223 for application data.
      - FRMPayload: the encrypted application payload.
  - MIC (4 bytes): Message Integrity Code, an AES-128 CMAC over the frame keyed
    by the network session key. The receiver recomputes and compares it to
    detect tampering or corruption.

4.5 Frame Counter (FCnt)
------------------------
Each end-device maintains an uplink frame counter (FCntUp) and the server
maintains a downlink frame counter (FCntDown). The counter is incremented on
every frame, is included in the MIC computation, and is checked by the receiver:
a frame whose counter is not greater than the last accepted counter is rejected
as a replay. This provides replay protection.

4.6 Security (AES-128)
----------------------
LoRaWAN security is rooted in AES-128 symmetric cryptography:
  - The MIC (4 bytes) is an AES-128-CMAC computed with the network session key
    (NwkSKey) and guarantees frame integrity and authenticity.
  - The application payload (FRMPayload) is encrypted with AES-128 in CTR mode
    using the application session key (AppSKey), so the network operator cannot
    read application data.
  - Session keys are derived during OTAA from the AppKey (root key) or
    pre-provisioned in ABP. End-to-end confidentiality is between the device and
    the application server.

================================================================================
5. CHANNEL ACCESS
================================================================================

5.1 ALOHA + Duty Cycle
----------------------
LoRaWAN end-devices use unslotted ALOHA: a device transmits whenever it has
data, with no listen-before-talk in most regions. To bound interference, the
regional parameters impose a duty cycle limit (e.g. 1% per sub-band in EU868),
restricting the fraction of time a device may occupy a channel. Some regions use
listen-before-talk (LBT) and/or dwell-time limits instead.

5.2 Receive Windows RX1 and RX2
-------------------------------
After every Class A uplink the device opens two receive windows:
  - RX1 opens RECEIVE_DELAY1 (default 1 s) after the end of the uplink, on the
    same channel and (by default) the same data rate as the uplink (offset by
    RX1DROffset).
  - RX2 opens RECEIVE_DELAY2 (default 2 s) after the uplink on a fixed,
    region-specific frequency and data rate (e.g. 869.525 MHz / DR0 in EU868).
If the device receives a valid downlink preamble in RX1 it does not open RX2.

5.3 Adaptive Data Rate (ADR)
----------------------------
Adaptive Data Rate lets the network optimize each device's spreading factor and
transmit power. When a device sets the ADR bit, the network server observes the
link margin (SNR) of received uplinks and issues a LinkADRReq MAC command to
raise the data rate (lower SF) and lower transmit power for devices with good
links, maximizing battery life and network capacity. The device confirms with
LinkADRAns. Mobile devices may disable ADR.

================================================================================
6. MAC COMMANDS
================================================================================

MAC commands manage the link between the end-device and the network server. They
are carried in the FOpts field (piggybacked) or in an FPort 0 frame. Each command
has a request (from the server) and an answer (from the device), or vice versa:
  - LinkCheckReq / LinkCheckAns      : device asks for link margin / gateway count.
  - LinkADRReq / LinkADRAns          : server sets data rate, TX power, channel mask.
  - DutyCycleReq / DutyCycleAns      : server sets the device's max duty cycle.
  - RXParamSetupReq / RXParamSetupAns: server sets RX1DROffset, RX2 DR, RX2 freq.
  - DevStatusReq / DevStatusAns      : server asks for battery level and margin.
  - NewChannelReq / NewChannelAns    : server defines/modifies a channel.
  - RXTimingSetupReq / RXTimingSetupAns : server sets RECEIVE_DELAY1.
  - TxParamSetupReq / TxParamSetupAns: server sets max EIRP and dwell time.

================================================================================
7. CONTROL / STATE BEHAVIOR (END-DEVICE)
================================================================================

7.1 End-device MAC states (Class A)
-----------------------------------
  - IDLE / SLEEP   : low-power; radio off; waiting for application data.
  - JOIN           : (OTAA) send Join-Request, open join receive windows, wait
                     for Join-Accept, derive session keys.
  - TX             : transmit an uplink LoRa frame (preamble, sync word, header,
                     payload, CRC) on a duty-cycle-permitted channel.
  - RX1_WAIT       : wait RECEIVE_DELAY1, then open RX1.
  - RX1            : receive on RX1 channel/DR; if downlink detected, demodulate.
  - RX2_WAIT       : if no RX1 downlink, wait until RECEIVE_DELAY2.
  - RX2            : receive on the fixed RX2 channel/DR.
  - PROCESS        : verify MIC with NwkSKey, check FCnt, decrypt FRMPayload with
                     AppSKey, process MAC commands, then return to IDLE/SLEEP.

7.2 Reset / power-on
--------------------
On power-up an OTAA device enters JOIN and must complete the join procedure
before sending data. An ABP device already holds DevAddr/NwkSKey/AppSKey and may
transmit immediately, restoring its frame counters from non-volatile memory.

================================================================================
8. REGISTER / PARAMETER MAP (MODEM CONFIGURATION)
================================================================================

The LoRa modem exposes configuration parameters (typically via an SPI register
interface to a transceiver such as the SX127x/SX126x):
  - Frequency (carrier)            : RF channel center frequency.
  - Spreading Factor (SF7-SF12)    : chirp spreading factor.
  - Bandwidth (125/250/500 kHz)    : channel bandwidth.
  - Coding Rate (4/5..4/8)         : FEC coding rate.
  - Preamble Length                : number of preamble symbols (default 8).
  - Sync Word                      : 0x34 public / 0x12 private network.
  - TX Power                       : output power (regional EIRP limit).
  - Header Mode                    : explicit / implicit.
  - CRC Enable                     : payload CRC on/off (on for uplinks).
  - LowDataRateOptimize            : set for long symbols (SF11/SF12 at 125 kHz).
These configure the PHY; the LoRaWAN session parameters (DevAddr, NwkSKey,
AppSKey, FCntUp, FCntDown, channel mask, RX1/RX2 settings) are MAC-layer state.

================================================================================
9. TEST / DEBUG / COMPLIANCE
================================================================================

Conformance is established by the LoRa Alliance Certification program against
the LoRaWAN L2 specification and the Regional Parameters. Observability includes:
  - DevStatusReq/Ans (battery level, demodulation margin).
  - LinkCheckReq/Ans (link margin, gateway count).
  - Frame-counter and MIC-failure counters.
  - RSSI and SNR of received frames (reported by the gateway/network server).
The LoRaWAN certification test harness exercises join, ADR, the MAC commands,
the receive-window timing, and the class behaviors.
