## IC Expert DB — relevant design-class knowledge (advisory)
Proven design-craft for similar designs. Apply the algorithm / interface / latency insight; the deterministic gates still decide PASS.

- **[serial-parallel-multiplier]** To author a functional-testbench GOLDEN for a serial-parallel / bit-serial arithmetic datapath (a parallel operand, a bit-serial operand and a bit-serial result on an N-bit datapath computing p = a OP b mod 2^N), do NOT copy the spec's prose 'expected' description into the vector as though it were a value, and do NOT read the product back from the DUT to 'confirm' it — either fabricates coverage. Instead COMPUTE the golden INDEPENDENTLY from the design's DECLARED function (product = a times b, sum = a+b, ... from the L2/L7 closed-form operator) as an N-bit constant, then verify the DUT's SERIAL output stream against it using the three framing facts the datapath is FREE to choose and therefore DECLARES in its interface contract (declaration.json bit_order / latency_cycles / integer_encoding, or the equivalent RTL-header 'DECLARED CHOICES' block): bit_order (LSB- vs MSB-first, for the serial operand AND the result), output latency_cycles, and integer_encoding (two's-complement is bit-identical to unsigned mod 2^N, so the output bit-pattern golden is the same either way). Choreography: drive the parallel operand held; stream the serial operand one bit per clock per the declared bit_order; sample the serial result at each clock; reassemble the product window [latency, latency+N) per bit_order before an === compare. These framing facts tell the oracle HOW to place the golden, never WHAT it is: a DUT that computes the wrong product fails at any declared framing, so the oracle stays falsifiable. When bit_order/latency are NOT declared the serial framing is not derivable — DEFER (leave the substance-floor testbench) rather than guess, because a fabricated golden is worse than an honest gap. Corner operands to always include: 0, 1, all-ones/MAX, MIN (signed), and -1. Same convention generalizes across the operator (+ - * & | ^ << >>) and across a fresh design of the same interface shape — it is keyed on the shape, not on any one design.
- **[serial-parallel-multiplier]** For a serial-parallel / bit-serial multiplier (parallel multiplicand x, serial multiplier y one bit per cycle, serial product p) that carries a stated clock-frequency target, do NOT author the behavioral form (accumulate `acc + (y?x:0)` then shift-and-emit each cycle): that places a full DATA_WIDTH-bit carry-propagate adder in the register-to-register path and misses an aggressive clock — measured on a 32-bit design it failed a 100 MHz / 10 ns sky130_fd_sc_hd target by ~24 ns worst slack. Instead use the SYSTOLIC carry-save array (Lyon bit-serial): hold the accumulator in redundant (sum, carry) form as two per-bit registers; each bit i is a single full-adder `{carry[i],sum[i]} = (x[i]&y) + s_hi[i] + creg[i]` where the >>1 accumulator shift is pure wiring (`s_hi = {1'b0, sreg[size-1:1]}`), then register `sreg<=sum; creg<=carry` and emit `p<=sum[0]`. The critical path is ONE full-adder (register-to-register) independent of width, so it closes timing at any reasonable clock while producing the IDENTICAL LSB-first serial product (low DATA_WIDTH bits = x*y mod 2^DATA_WIDTH) with the same 1-cycle output latency. Same result on the same design: systolic form met the 100 MHz target at +3.82 ns slack, DRC-clean and LVS-matched. General rule: when a bit-serial datapath has a clock target, redundant carry-save state beats a per-cycle carry-propagate accumulator.
- **[apb-csr-shift-register]** When a spec says a register "updates on the rising edge of <signal>", model that signal as an actual clock (`always @(posedge signal or negedge presetn)`) rather than sampling it in the main clock domain — the checker drives that signal as a clock edge, so a synchronizer/edge-detector approach would miss updates. Correspondingly, implement glitch-free clock gating by latching the enable on the OPPOSITE (negedge) clock edge before ANDing with the clock (`gated_clk = pclk & enable_latched_on_negedge`), and give misprediction-restore strict priority over the normal LSB shift-in. For the APB CSR wrapper: register-map reads must zero-extend reserved bits, read-only registers must silently ignore writes, and pslverr must assert only on invalid addresses during a qualified (pselx && penable) access with zero wait states (pready held high).
- **[integer-clock-divider]** For memory-mapped / AXI-Lite register reads, make the read-data mux COMBINATIONAL (zero-latency, keyed on the address) so a read reflects the live register value in the same cycle it is addressed. A registered/pipelined axi_rdata adds one cycle of latency and returns STALE data, failing read-after-write and live-counter read-back checks. Verified: replacing the draft's `always@(posedge clk)` read block with a combinational `always@(*)` mux makes the case PASS.
- **[integer-clock-divider]** Integer clock divider: divided-clock outputs described as 'toggled'/'reset-initialized' are REGISTERS, not a combinational decode of the current count. The CANONICAL odd-divisor 50%-duty divider is the OR of a posedge half-rate LEVEL and a negedge half-rate LEVEL: use one counter cnt1 on posedge and cnt2 on negedge, each counting 0..NUM_DIV-1, and register each level as `clk_div_k <= (cnt_k < NUM_DIV/2)` (a LEVEL that is high for the first floor(NUM_DIV/2) counts, NOT a single toggle-at-a-point — a lone toggle every NUM_DIV counts would divide by 2*NUM_DIV, not NUM_DIV). The reset value of each clk_div_k is DERIVED, not guessed: cnt resets to 0 and 0 < NUM_DIV/2, so the level is 1 at reset — reset clk_div_k to 1'b1 to match its own cnt==0 level. Combine with `clk_div = clk_div1 | clk_div2`. A combinational `assign clk_div=(cnt<LIMIT)` or a toggle-on-limit form shifts the phase and fails a cycle-accurate check even when the average ratio is right.
